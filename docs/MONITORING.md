# 서비스·작업 모니터링

관리자 **모니터링** 메뉴에서 **서비스 상태 / 프로젝트 작업**으로 범위를 고른다. 서비스 상태는 플랫폼 공통이며 프로젝트 선택과 무관하다. 프로젝트 작업에서는 프로젝트와 **조회 환경**을 선택해 Keycloak 환경 반영 Job(`ENVIRONMENT_PROVISION`)을 조회한다.

## 플랫폼 서비스 상태

현재 Compose의 프로젝트·파일·알림 서비스별 단일 인스턴스를 조회한다. `readiness`의 서비스 준비 상태·DB 연결을 검사하며 정상 응답, 준비 안 됨, 연결 확인 실패, 해석할 수 없는 응답을 구분한다. 응답 정상은 로그인·메일 발송 등 모든 업무의 성공을 보장하지 않는다. 상태 확인과 지표 조회는 독립적이며 한쪽 실패가 다른 쪽을 0건 또는 정상으로 바꾸지 않는다.

Spring Boot가 이미 수집하는 `http.server.requests`의 요청 수와 총 처리 시간을 사용한다. [Spring Boot 지표 안내](https://docs.spring.io/spring-boot/reference/actuator/metrics.html)와 [Micrometer Timer](https://docs.micrometer.io/micrometer/reference/concepts/timers.html)를 따른다.

| 표시 | 기준 |
| --- | --- |
| 처리 요청 | 해당 프로세스 재시작 이후 완료된 HTTP 요청 수 |
| 클라이언트 오류 | HTTP 4xx 건수. 인증·권한 거절도 포함 |
| 서버 오류 / 서버 오류율 | HTTP 5xx 건수 / 전체 처리 요청 대비 비율. 0~100% 고정 눈금 |
| 평균 처리 시간 | 총 서비스 내부 HTTP 처리 시간 ÷ 처리 요청 수, 밀리초. 서비스 공통 눈금 |
| 요청 없음 | 수집은 성공했지만 요청 수가 0. 오류율·평균은 null |
| 미수집 | 수집 연결 미설정 또는 조회 실패. 0건으로 대체하지 않음 |

내부 API·거절된 요청·경로가 매핑되지 않은 요청을 포함하고, 식별 가능한 Actuator 경로·내부 모니터링 조회·관리자 서비스 지표 조회는 제외한다. Nginx에서 차단된 요청, 인터넷·프록시 구간 시간, 아직 끝나지 않은 요청은 포함하지 않는다. 경로가 식별되지 않은 거절 요청은 제외 대상인지 구분할 수 없어 합계에 포함될 수 있다. 실제 검수에서 의도적으로 발생시킨 4xx/5xx도 집계되며 임의로 지우지 않는다.

서비스마다 집계 시작·요청 내용이 다르므로 성능 순위로 해석하지 않는다. 서로 다른 계측기의 조회는 원자적 스냅샷이 아니므로 동시 요청 중에는 아주 작은 시점 차이가 있을 수 있다. 시작 시각·측정 시각·프로세스 식별자를 반환한다. 누적값은 프로세스 메모리에서만 보유하며 재시작 시 초기화한다. DB 이력이나 시간대별 추이는 아직 저장하지 않는다.

`GET /api/v1/admin/service-metrics`는 관리자 JWT 전용이다. 서버 API 키·일반 회원은 사용할 수 없다. 프로젝트 서비스가 고정된 내부 주소 3개에만 연결하며 각 HTTP 요청은 최대 1초, 연결은 1초로 제한하고 리다이렉트는 따르지 않는다. 최대 6개 요청을 순서대로 실행하고 결과를 10초간 공유해 반복 조회 부하를 제한한다. 각 결과의 확인 시각은 다를 수 있으며 최상위 측정 시각은 모든 확인이 끝난 시점이다.

내부 `GET /internal/v1/monitoring`은 별도 `PLATFORM_MONITORING_SECRET` / `X-Platform-Monitoring-Key`로 제한한다. 메일·이벤트 키와 분리하며 Nginx 외부 경로와 OpenAPI에는 공개하지 않는다. 키가 비어 있으면 내부 조회를 거부하고 화면에는 지표 수집 미설정으로 표시한다. `.env`가 있는 환경은 `python scripts/init-env.py --upgrade`로 빠진 키만 생성한 뒤 프로젝트·파일·알림 서비스를 다시 생성한다. 실제 키는 출력·커밋하지 않는다. 원시 경로·태그·헤더·요청 본문·환경변수는 API에 반환하지 않으며 성공 응답은 `Cache-Control: no-store`다.

화면은 30초 자동 갱신·수동 새로고침, 숨긴 화면의 갱신 중지, 1분 이상 지난 값 안내를 제공한다. 전체 조회 실패 시 이전 값임을 표시하고 개별 서비스 수집 실패는 그 서비스만 미수집으로 표시한다. 새 서비스·포트·수집 프로세스는 없으며, 조회 중단은 화면을 닫거나 자동 갱신을 끄는 방식이다. 공통 HTTP 모듈이 기존 Actuator의 Micrometer 타입을 사용하며 새 외부 관측 제품을 도입하지 않았다.

프로젝트 서비스 자체가 중단되면 이 화면도 조회할 수 없다. 외부 감시·서비스 장애 알림, Keycloak·Nginx·디스크, 시계열·최근 구간 오류율·보존 기간·다중 인스턴스 집계는 후속 범위다.

## 화면과 차트

PC에서는 현재 작업 상태와 최근 24시간 처리 결과를 나란히, 좁은 화면에서는 위아래로 표시한다. 완료·최종 실패·취소는 0부터 시작하는 공통 눈금의 막대 차트로 비교하며 이름과 정확한 건수를 함께 보여 준다. 모든 값이 0이면 막대를 채우지 않고 종료된 작업이 없다고 안내한다. 시간대별 추이 그래프는 아직 제공하지 않는다.

| 수치 | 집계 기준 |
| --- | --- |
| 대기 중인 작업 | 최초 대기(`QUEUED`) + 재시도 대기(`RETRY_WAIT`) |
| 최초 대기 / 재시도 대기 / 실행 중 | 각각의 현재 상태 수. 현재 환경당 활성 Job은 하나 |
| 실행 예정 시각이 지난 대기 | 대기 중이며 `next_run_at ≤ measuredAt`. 재시도 예약 시간이 남은 작업 제외 |
| 최장 대기 시간 | 현재 대기 상태가 시작된 `updated_at`부터 측정 시각까지의 초. 실행·종료된 작업 제외, 대기 없으면 `null` / 화면에서는 ‘대기 없음’ |
| 최근 24시간 완료·최종 실패·취소 | `completed_at`이 `windowFrom` 이상, `measuredAt` 미만인 각 최종 상태. 개별 시도의 실패 수가 아님 |

최장 대기 시간은 최초 접수부터의 총 소요 시간이 아니다. 재시도 대기로 바뀌면 새 대기 구간을 측정한다. 미래 시각으로 기록된 대기 시간은 음수 대신 0초로 제한한다. 원래 Job이 실패한 뒤 후속 Job이 성공해도, 원래 실패 기록은 24시간 집계에 남는다. 미해결 장애 수나 미확인 알림 수와 다르다.

**대기 작업 보기·재시도 대기 보기·실행 중 작업 보기·전체 기간 실패 작업 보기**는 같은 환경의 작업 목록에 상태 필터를 적용한다. 실패 목록에는 기간 제한을 걸지 않는다. 작업 목록은 접수 시각, 차트는 완료 시각 기준이어서 목록 건수와 차트 건수가 같지 않을 수 있다. **운영 알림 보기**도 같은 범위를 유지한다.

## 갱신과 오류

- 기본은 조회 종료 후 30초마다 갱신한다. 자동 갱신을 끄거나 **지표 새로고침**으로 직접 조회할 수 있다.
- 화면이 숨겨지면 자동 조회를 쉬고, 다시 보일 때 자동 갱신이 켜져 있으면 바로 조회한다. 이미 보낸 요청은 완료될 수 있다.
- 측정값을 화면에서 임의로 증가시키지 않는다. 측정 시각부터 1분 이상 지나면 오래된 값이라는 안내를 표시한다. 서버와 브라우저 시계가 맞아야 경과 안내가 정확하다.
- 첫 조회 실패는 수치를 표시하지 않는다. 갱신 실패는 이전 측정값과 오류를 함께 표시하며 0건으로 바꾸지 않는다. 다른 환경으로 바꾸면 이전 값은 비우고, 이전 요청이 늦게 도착해도 새 환경을 덮어쓰지 않는다.

## API·집계

`GET /api/v1/admin/environments/{id}/job-metrics`는 관리자 JWT 전용이다. 서버 API 키와 일반 회원은 사용할 수 없다. 존재하는 환경에 Job이 없으면 건수 0과 대기 시각/시간 `null`, 존재하지 않는 환경은 404 `RESOURCE_NOT_FOUND`를 반환한다. 중지 프로젝트도 이력을 조회할 수 있다.

응답은 `projectId`, `environmentId`, `measuredAt`, `windowFrom`, `queued`, `retryWaiting`, `running`, `dueWaiting`, `oldestWaitingAt`, `oldestWaitingSeconds`, `succeededLast24Hours`, `failedLast24Hours`, `cancelledLast24Hours`다. [프로젝트 API 안내](PROJECT_API.md)와 배포된 OpenAPI의 `JobMetrics` 모델을 기준으로 사용한다.

프로젝트 서비스가 자신의 DB를 한 번 조회해 같은 스냅샷·DB 시각으로 계산한다. 활성 작업과 최근 24시간에 종료된 작업만 합산한다. V9의 환경/완료 시각 인덱스와 기존 활성 작업 인덱스를 사용 가능한 조회 조건으로 둔다. 별도 집계 테이블·의존성·수집 프로세스·외부 포트는 추가하지 않았다. 이력이 많아졌을 때 실제 실행 계획과 응답 시간을 확인해야 한다.

## 적체 경보 설정

모니터링은 **작업 현황 / 적체 경보 설정** 탭으로 나뉜다. 설정의 기본은 꺼짐, 대기 기준 300초(5분), 연속 2회다. 대기 기준은 60~86,400초, 연속 횟수는 1~10회까지 지정한다. 설정 저장 전 대상과 영향을 확인하며 저장 중에는 메뉴·탭·환경 이동을 막는다. 저장하지 않은 입력은 이동·새로고침 때 버린다.

저장 충돌이나 오류가 나면 확인창을 닫아도 저장을 잠근다. **설정 새로고침**이 성공해야 다시 편집한 값을 저장할 수 있다. 조회 실패 때는 이전 입력으로 재시도하지 않으며, 마지막 검사 시각과 연속 횟수는 수동 새로고침으로 확인한다.

- 프로젝트 서비스 내부 스케줄러가 5초마다 최대 100개 환경을 확인한다. 각 환경의 검사는 DB의 `next_check_at`과 행 잠금으로 최소 30초 간격을 유지한다. 여러 인스턴스가 동시에 실행돼도 같은 환경을 중복 검사하지 않는다. 지연이 생기면 검사 간격은 길어질 수 있다.
- `QUEUED`/`RETRY_WAIT`이고 실행 예약 시각이 지났으며, 현재 대기 상태의 `updated_at`부터 기준 시간 이상 지난 작업이 대상이다. 예약 시간이 남은 재시도와 RUNNING은 제외한다. 최초 접수부터의 총 소요 시간과 다르다.
- 같은 작업·같은 대기 시작 시각의 초과를 연속 확인하면 `job.backlogged`를 한 번 생성한다. 중간에 조건에서 벗어나거나 작업/대기 구간이 바뀌면 발생 횟수를 새로 센다. 열려 있는 동안 반복 이벤트·정기 재알림은 만들지 않는다.
- 열린 사건의 작업이 적체 기준에서 벗어난 것을 같은 횟수만큼 확인하면 `job.backlog_recovered`를 생성한다. 실행 시작·성공·실패·취소·새 대기 구간 등으로 대기 적체 조건에서 벗어날 수 있다. **적체 해소는 작업 성공이나 전체 서비스 복구를 보장하지 않는다.** 이후 같은 작업이 다시 적체되면 새 사건으로 기록한다.
- 마지막 검사와 90초 넘게 차이 나면 발생·해소 연속 횟수를 초기화한다. 프로세스 재시작은 DB에 남은 사건과 관측 시각을 이어받으며, 검사 실패는 해소로 처리하지 않는다. 서버/DB 자체 중단을 탐지하는 외부 감시기는 아니므로 마지막 검사 시각도 확인한다.
- 설정을 저장하면 열린 사건을 `job.backlog_closed`로 종료하고 연속 횟수를 초기화한다. ‘감시 종료’는 실제 해소가 아니며 복구 이메일을 보내지 않는다. 종료 이벤트를 수신할 때 아직 PENDING인 해당 적체 이메일은 취소하되 이미 시작한 발송은 회수하지 않는다. 두 서비스 사이 전달이 지연되는 동안에는 이전 대기 이메일이 시작될 수 있다.
- 이메일은 기존 운영 알림 수신 설정을 사용한다. 감시를 켜는 것만으로 수신 설정을 켜지 않는다. 최종 실패와 적체의 억제 범위는 분리되며 DEV는 모의 발송만 허용한다. 이벤트가 역순으로 도착해도 사건 ID로 연결하고 과거 발생·설명할 수 없는 선행 해소의 이메일은 생략한다.

`GET /api/v1/admin/environments/{id}/job-backlog-settings`는 설정, 현재 사건 ID·작업 ID, 마지막 검사, 연속 횟수, 서버 감시 가용 여부를 반환한다. `PUT` 본문은 `enabled`, `thresholdSeconds`, `consecutiveChecks`, `revision`이다. 관리자 JWT 전용이며 없는 환경 404, 잘못된 범위 400, revision 충돌 409 `SETTINGS_CHANGED`, 서버 이벤트 전달 비활성 상태에서 켜기 503을 반환한다. 비활성화는 감시기가 꺼져 있어도 가능하다.

V10의 `job_backlog_settings`와 버전별 `job_backlog_settings_audit`에 기록한다. 설정과 종료 이벤트·감사는 같은 트랜잭션이며, 발생/해소와 관측 상태·감사·Outbox도 함께 저장한다. 사건의 `targetRevision`은 **적체 설정 버전**이고 최종 Job 이벤트의 환경 설정 버전과 다르다. `causationId`는 해소/종료 대상의 발생 이벤트 ID다. 기존 Outbox 재시도와 Job 상세의 이벤트 전달 이력을 사용한다.

`platform.events.enabled`가 꺼지면 감시 스케줄러도 멈춘다. 기존 `PLATFORM_EVENTS_ENABLED` 환경변수와 Compose 기동/중지 방식을 사용한다. 환경별 감시만 중지하려면 화면에서 설정을 끈다. 새 서비스·의존성·외부 포트는 없다.

## 남은 범위

전체 프로젝트 통합 조회, 디스크 지표, 실행 중 작업의 장시간 점유 경보, 시계열 수집·보존 정책과 서비스 지표의 임계값 경보는 후속 작업이다. 기존 최종 실패·복구 알림과 이메일 설정은 [운영 알림 지침](OPERATIONAL_ALERTS.md)을 따른다. 이 화면 추가가 F-07 전체 완료를 뜻하지 않는다.
