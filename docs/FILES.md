# 파일 서비스

## 현재 제공 범위

서버 간 파일 연동의 첫 단위다. 업로드 세션 생성, 최대 5,000,000,000바이트 파일의 분할·재개, SHA-256 검증, 목록·정보·다운로드·삭제와 공개 범위 변경을 제공한다. 프로젝트·환경은 API 키에서 결정하며 요청자가 임의로 지정하지 않는다.

관리자 전용 파일 메뉴에서 멀티/드래그 업로드, 파일별 진행률·실패 안내, 일시정지·원본 재선택 후 재개, 목록·다운로드·공개 범위·삭제를 제공한다. 이용자 JWT/위임 업로드, 비밀번호 공유, 미리보기·썸네일·중복 안내, 보존 코드 관리·완료 파일 자동 삭제는 **후속 구현**이다. 이 항목들은 첫 출시 범위에서 제외하지 않는다. 현재는 원본 다운로드 URL만 반환하며 아직 없는 미리보기 URL이나 처리 결과를 만들지 않는다.

## 관리자 파일 화면

왼쪽 **파일** 메뉴에서 프로젝트·조회 환경을 선택한다. **파일 목록 / 업로드·재개** 탭으로 작업을 나누고 다른 메뉴와 선택 범위를 공유한다. 업로드는 한 번에 20개까지 대기하고 하나씩 전송한다. 새 파일의 공개 범위는 추가 전에 선택하며 기본은 공개, 보존 코드는 `default`다.

원본 확인은 Web Worker의 `hash-wasm` SHA-256으로 4MiB씩 읽고 조각 검증은 최대 8MiB씩 수행한다. 파일 전체를 메모리에 올리지 않는다. 전송 중에는 프로젝트·환경 이동을 막고, 일시정지하면 이동할 수 있다. 새로고침·다른 화면 방문 후에는 같은 관리자 소유의 미완료 세션을 조회하고 같은 원본을 재선택한다. 크기와 전체 해시가 다르면 전송하지 않는다. 세션 생성 전 원본 확인 중이던 파일은 다시 추가해야 한다. 생성 응답이 유실되어도 요청 ID로 로컬 항목과 서버 세션을 합쳐 중복 표시하지 않는다. 네트워크 오류의 조각 재시도는 최대 2회이며 서버 확정 위치를 다시 읽는다. 연결 복구 후 사용자가 재시도할 수 있다.

관리 API는 `/api/v1/files/admin/environments/{environmentId}` 아래에 있으며 해당 플랫폼 관리자 realm의 서명·발급자·대상(`platform-admin-api`)·`platform-admin` 역할을 검증한다. 관리자 토큰을 사용하고 서버 API 키를 브라우저에 전달하지 않는다. 세션 소유권은 관리자/서버 키 종류와 식별자를 함께 확인한다. 완료 파일은 같은 환경의 관리자가 관리할 수 있다. 매 요청 프로젝트·환경의 사용 가능 상태를 내부 API로 확인한다.

다운로드 버튼은 관리자 인증 후 최대 60초의 일회용 링크를 발급한다. 유효 기간은 관리자 토큰 만료를 넘지 않으며 DB에는 무작위 비밀값의 SHA-256만 보관한다. 링크를 가진 사람은 1회 다운로드할 수 있으므로 공유하지 않는다. 같은 파일에 새 링크를 발급하면 이전 미사용 링크를 무효화한다. 공개 범위 변경·삭제도 미사용 링크를 폐기한다. HEAD 요청은 소비 없이 거부하고, GET은 원자적으로 소비한 뒤 현재 파일·환경 상태를 재검사한다. 실패했다면 새로 다운로드를 요청한다. 이미 시작된 전송은 회수하지 않는다. 브라우저 기본 다운로드를 사용하므로 전체 파일을 Blob으로 복사하지 않는다.

파일 명세는 서버 키 API 11개 작업, 관리자 API 10개 작업과 일회용 다운로드 1개 작업을 포함한 **16개 경로/22개 작업**이다. 관리자용 업로드 목록은 자기 세션만 반환한다. 이용자 realm의 JWT를 관리자 API 권한으로 인정하지 않는다.

## 인증과 접근 범위

| 권한 | 허용 동작 |
|---|---|
| `files:read` | 같은 환경의 파일 목록·정보, 비공개 원본, 파일 API 명세 |
| `files:write` | 업로드 생성·상태·전송·완료·취소, 같은 환경 파일의 공개 범위 변경 |
| `files:delete` | 같은 환경의 완료 파일 삭제 |

관리자 화면의 **프로젝트 → API 키**에서 필요한 권한을 선택해 새 키를 발급한다. 기본 권한은 여전히 `integration:read`뿐이며 기존 키를 자동 확장하지 않는다. `X-Platform-Key`에 서버 API 키를 보낸다. 브라우저 코드·URL·문서·로그에 키를 넣지 않는다. 이용자별 파일 관리 권한은 아직 이 API가 판단하지 않으므로 호스트 서버가 자기 이용자의 접근 권한을 확인한 뒤 호출해야 한다.

진행 중 세션은 생성한 키에 귀속된다. 같은 환경의 다른 키도 해당 세션을 재개하거나 취소할 수 없다. 키가 폐기·만료되면 세션은 더 이상 재개할 수 없고 24시간 만료 후 정리된다. 완료 파일은 해당 환경의 권한 있는 서버 키가 관리한다. 다른 프로젝트·환경에서 ID를 알아도 관리·비공개 다운로드는 404로 거부한다.

각 보호 요청마다 파일 서비스가 프로젝트 서비스의 내부 API로 키·권한·환경 상태를 검사한다. 인증 결과를 캐시하지 않는다. 두 서비스는 별도 DB를 사용하며 `PLATFORM_FILES_SECRET`은 이 통신만 인증한다. 메일·이벤트·모니터링 비밀값과 구분하고 Nginx는 내부 API를 공개하지 않는다. 키 폐기·프로젝트 중지는 다음 요청부터 적용되며 이미 시작된 전송을 회수하지 않는다. 프로젝트 중지 또는 환경 미준비 시 공개 다운로드도 차단한다. 프로젝트 서비스가 응답하지 않으면 접근을 허용하지 않고 503을 반환한다.

## 업로드 계약

OpenAPI 원본은 [file-service/openapi.json](../services/file-service/src/main/resources/openapi.json)이며 `GET /api/v1/files/openapi`로도 조회한다(`files:read`). 관리자 개발자 포털의 통합 탐색은 후속 작업이다. 프로젝트 API의 기존 OpenAPI 명세와 별도로 제공한다.

| 순서 | 요청 | 결과 |
|---|---|---|
| 1 | `POST /api/v1/files/uploads` | 세션 ID, 확정 수신 위치, 만료 시각, 조각 상한 |
| 2 | `PATCH /api/v1/files/uploads/{id}` | 조각 저장 후 새 수신 위치 |
| 재개 | `GET /api/v1/files/uploads/{id}` | 서버가 확정한 위치부터 다시 전송 |
| 완료 | `POST /api/v1/files/uploads/{id}/complete` | 전체 크기·해시 확인 후 파일 정보 |
| 취소 | `DELETE /api/v1/files/uploads/{id}` | 미완료 세션 취소, 204 |

생성 본문 예:

```json
{
  "requestId": "73c47913-d64b-455c-ab97-8a44e4fa7da1",
  "originalName": "보고서.pdf",
  "size": 12345,
  "sha256": "원본 전체 바이트의 소문자 SHA-256 64자리",
  "visibility": "PUBLIC",
  "retentionCode": "default"
}
```

`requestId`는 호출자가 파일 항목마다 생성하는 UUID다. 같은 키·환경에서 같은 생성 본문을 재전송하면 같은 세션을 반환한다. 다른 본문으로 같은 ID를 재사용하면 409다. 나중에 공개 범위를 변경해도 최초 생성 요청의 재시도는 같은 세션을 가리킨다. 새 업로드는 새 요청 ID를 사용한다.

조각은 `Content-Type: application/octet-stream`, `Content-Length`, `Upload-Offset`, `X-Chunk-SHA256` 헤더와 원시 바이트를 보낸다. 조각 하나는 1~8,388,608바이트(8MiB), 위치는 서버의 `receivedBytes`와 같아야 한다. 한 파일은 순서대로 보내고, 여러 파일은 별도 세션으로 처리한다. 해시는 실제 조각 바이트의 소문자 SHA-256이다. 선언 길이·해시가 다르거나 전송이 끊기면 해당 조각을 확정하지 않는다. 조각 전체를 메모리에 적재하지 않고 64KiB 버퍼로 기록한다.

응답을 받지 못했다면 상태를 조회한다. 이미 확정된 위치에 같은 조각을 다시 보내면 409 `FILE_OFFSET_CONFLICT`이며 중복 저장하지 않는다. 일시정지는 다음 조각을 보내지 않는 것이다. 원본 파일은 호출자가 보관하고 재개 시 같은 내용을 제공해야 한다. 조각 해시와 완료 시 전체 해시를 모두 확인하므로 같은 이름만으로 파일을 판정하지 않는다.

[tus 1.0 명세](https://tus.io/protocols/resumable-upload)의 확정 위치·충돌·만료 방식을 검토했다. 이번 구현은 기존 JSON 오류/키 권한과 완료 검증 API에 맞춘 플랫폼 계약이며 **tus 호환 서버가 아니다**. 별도 tus 서버나 저장소 SDK는 도입하지 않았다.

DB 행 잠금으로 같은 세션의 동시 요청을 직렬화한다. 파일을 디스크에 동기화한 뒤 수신 위치를 커밋하며, 재시작/DB 롤백으로 뒤에 남은 바이트는 다음 전송 전 확정 위치로 잘라낸다. 완료 시 전체 파일을 스트리밍으로 해시 검사한 후 `READY`로 바꾸며 완료 재시도는 같은 파일 ID를 반환한다. 크기 0 파일은 조각 전송 없이 완료한다. 원본 이름은 경로로 사용하지 않는다.

세션 만료는 생성 후 24시간으로 고정되며 일시정지·재개로 연장하지 않는다. 만료 시각 이후 완료/전송은 거부한다. 완료 파일을 세션 취소로 지울 수 없으며 별도의 삭제 권한이 필요하다.

## 조회·다운로드·삭제

| 요청 | 용도 |
|---|---|
| `GET /api/v1/files?limit=20&offset=0` | 완료 파일만 조회, limit 1~100 |
| `GET /api/v1/files/{id}` | 파일 이름·크기·검증 해시·공개 범위·보존 코드·최근 이용 시각 |
| `GET /api/v1/files/{id}/download` | 원본 전체 다운로드 |
| `PUT /api/v1/files/{id}/visibility` | `{"visibility":"PRIVATE"}` 또는 `PUBLIC` |
| `DELETE /api/v1/files/{id}` | 즉시 논리 삭제, 204; 같은 환경에서 재시도 가능 |

기본은 `PUBLIC`으로 URL을 알면 원본을 받을 수 있다. 목록·메타데이터·관리는 공개하지 않는다. 비공개 파일의 익명 다운로드는 존재하지 않는 파일과 같은 404이며, 같은 환경의 `files:read` 키가 있어야 한다.

현재 모든 원본은 `application/octet-stream`과 `Content-Disposition: attachment`로 내려준다. HTML/SVG도 같은 출처의 실행 가능한 문서로 열지 않는다. `nosniff`, CSP sandbox, `no-store`를 적용하고 공개→비공개 전환 후 플랫폼 캐시 우회를 막는다. 이미 사용자가 내려받은 파일은 회수할 수 없다. Range 다운로드는 아직 지원하지 않아 전체 200으로 반환한다. HEAD는 인증/헤더 확인만 하며 이용 시각을 늘리지 않는다.

최초 이용 시각은 완료 시각이다. 원본 전체 전송이 오류 없이 끝난 뒤 `lastUsedAt`을 갱신한다. 목록·정보·실패·HEAD는 갱신하지 않는다. 네트워크 전송 성공은 이용자가 파일을 실제 열었다는 보장이 아니다.

파일 삭제는 DB 상태와 감사 기록을 같은 트랜잭션에 저장해 즉시 신규 접근을 차단한다. 60초 주기 정리기가 취소·만료·삭제 파일을 최대 100개씩 물리 삭제하며 실패는 다음 회차에 재시도한다. 재시작 후에도 대상 상태를 유지한다. 디스크 정리 완료 전에는 해당 파일의 예약 용량을 반환하지 않는다. **완료 파일의 보존 기간에 따른 자동 삭제는 아직 실행하지 않는다.**

## 저장소와 운영

- 파일 DB: `platform_file`. 메타데이터·세션·보존 코드 참조·감사 기록을 저장한다.
- 원본: Compose `file-data` 영속 볼륨의 `/app/storage`. 비특권 앱 사용자 소유이며 UUID 기반 이름만 사용한다. Nginx에서 이 경로를 직접 공개하지 않는다.
- 처음 사용하는 환경에 `default`(365일), `tmp`(1일), `영구`(기간 없음) 정책 행을 만든다. 미등록 코드는 거부한다. 정책 수정·사용자 코드·삭제 유예·자동 삭제는 다음 단위에서 구현하며 현재는 코드와 최근 이용 시각만 보관한다. ‘1년’ 계산은 자동 삭제 구현 시 확정한다.
- 기본 환경 예약 한도: `FILE_ENVIRONMENT_QUOTA=50000000000`(50GB), 미완료 세션 수: `FILE_PENDING_LIMIT=20`. 파일 크기를 미리 예약해 완료 파일과 진행 중 업로드를 함께 계산한다. 단일 공유 디스크에서 모든 환경의 남은 예약 바이트도 확인하고 실제 여유 256MiB를 남긴다. 전체 DB 메타데이터 수/요청 빈도 제한은 별도 운영 보완 사항이다.
- 단일 파일 서비스와 로컬 영속 볼륨으로 시작한다. 인스턴스를 여러 호스트에 복제하기 전 공유 저장소·분산 파일 잠금/배치 전략을 별도로 검토한다. DB만 복구하거나 볼륨만 복구하면 일치하지 않을 수 있어 둘을 함께 백업한다. 전원 장애·디스크 장애 복구는 별도 검수 대상이다.
- Nginx 파일 경로만 요청 상한 8MiB, 본문 대기 30초, 응답 대기 300초다. 외부 NPM도 이 크기/시간을 허용해야 한다. 다른 API의 기존 1MiB 상한은 유지한다. HTTP 진입은 기존 30140이며 새 외부 포트를 열지 않는다.

설정 추가는 `python scripts/init-env.py --upgrade`로 한다. 기존 `.env` 값을 덮어쓰지 않는다. 파일/프로젝트/Nginx 이미지를 빌드한 뒤 해당 서비스만 재생성한다. 기존 볼륨에 사용자 파일을 임의로 복사하거나 이전 파일 서비스를 이전하지 않는다.

## 검증과 재개

격리 DB 검증은 운영 Compose와 결합하지 않는다.

```powershell
docker compose -p platform-job-checks -f compose.jobs-test.yml up --abort-on-container-exit --exit-code-from check
docker compose -p platform-job-checks -f compose.jobs-test.yml down
```

개발 서버 실제 검사는 전용 프로젝트 2개와 DEV/PROD 환경을 만들며 일반 회원·기존 프로젝트를 변경하지 않는다. 검사 후 키 폐기·파일 삭제/취소·프로젝트 중지·검사 관리자 세션 로그아웃을 수행하고 감사 이력은 남긴다. 중간 상태 파일에는 단기 검사 키가 있어 Git 제외 `output/playwright/file-check.json`에만 두며 정상 종료 후 삭제한다.

```powershell
docker compose -f compose.yml -f compose.dev.yml --profile test run --rm --no-deps file-check --phase start
docker compose -f compose.yml -f compose.dev.yml restart file-service
# file-service가 healthy가 된 뒤
docker compose -f compose.yml -f compose.dev.yml --profile test run --rm --no-deps file-check --phase finish
```

중간 종료 시 `--phase cleanup`을 사용한다. 검사 키가 만료되면 관리자에서 해당 검사 프로젝트·키를 확인해 정리하고, 미완료 원본은 세션 만료 정리기가 처리한다. 검사 스크립트는 비밀값을 출력하지 않는다. 기본 실제 전송 샘플은 약 7MB이며 5GB 선언 상한/초과 거부와 실제 5GB 전체 전송 성능은 다른 검증이다. 실제 실행 결과와 미검증 범위는 [STATUS](STATUS.md)를 따른다.

다음 단위는 독립 **파일** 메뉴와 프로젝트·환경 선택, 관리자 인증 연결, 멀티/드래그·진행률·재시도·재개 UI다. 이어 보존 정책·비밀번호 공유, 비동기 썸네일/미리보기·중복 안내를 구현한다. 모니터링 추가 확장은 사용자 요청 시 재개한다.
