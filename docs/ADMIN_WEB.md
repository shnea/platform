# 관리자 화면

http://localhost:30140/ 에서 접속한다. 최초 플랫폼 관리자 계정은 `admin`, 비밀번호는 로컬 `.env`의 `PLATFORM_ADMIN_PASSWORD`다. `KEYCLOAK_ADMIN_PASSWORD`를 쓰는 master 관리자와 다르다. 먼저 README의 `identity-setup`을 실행해야 한다.

어두운 테마가 기본이며 상단 버튼으로 밝은 테마를 선택할 수 있다. 테마 선택만 브라우저에 저장하며 로그인 토큰·API 키는 영구 저장하지 않는다. 서버 배포 모드(개발·운영)를 메뉴 영역에 표시한다. 각 프로젝트의 DEV·PROD 로그인 환경과 서버 배포 모드는 서로 다른 개념이다.

## 사용 순서

1. **프로젝트 만들기**에서 표시 이름과 고유 코드를 등록한다. 코드는 소문자로 시작하는 2~40자이며 소문자·숫자·하이픈만 사용한다.
2. 프로젝트를 열고 **환경 만들기**에서 DEV 또는 PROD, 정확한 로그인 콜백 주소, 일반 가입 허용 여부를 정한다. 계정은 프로젝트·환경마다 분리된다.
3. **반영 완료**를 확인한다. 실패·대기는 키 사용을 차단하며 **다시 반영**으로 재시도할 수 있다. 중지된 프로젝트의 반영 완료는 로그인 영역 비활성화까지 반영되었다는 뜻이다.
4. **서버 API 키 → 키 발급**을 실행한다. 원문은 이때만 보이므로 서버 비밀값 저장소에 보관한다. 창을 닫으면 다시 볼 수 없다. 발급 창은 **만료 없음**이 기본이다. 필요하면 **만료일 지정**을 선택하고 현재 기기 시간대 기준의 미래 날짜·시간을 입력한다. 지정한 시점부터 접근을 차단하며, 필요 없으면 만료 전에도 **폐기**할 수 있다. 기존에 발급한 90일 키는 원래 만료일을 표시한다. 최근 100개 메타데이터를 표시하고 오래된 키도 ID를 알면 API로 폐기할 수 있다.
5. **설정 변경**에서 가입·콜백을 변경한다. 다른 화면에서 먼저 수정했으면 충돌 안내가 나오므로 닫고 새로고침한 뒤 다시 변경한다.
6. **중지/재개**는 확인 창에서 영향을 읽고 실행한다. 프로젝트의 API 키 접근을 먼저 차단하고 각 Keycloak realm에 적용한다. 기존 access token은 만료 전까지 외부 서비스에서 유효할 수 있다. 자세한 범위는 PROJECT_API.md를 따른다.
7. **감사 이력**에서 최근 100개 작업·대상 ID·시간을 확인한다.

## 브라우저 검수

실제 검수 시 새 테스트 프로젝트를 사용한다. 파일·알림·에디터 메뉴나 가짜 업무 데이터는 제공하지 않는다.

- 로그인 → 프로젝트 생성 → DEV 환경 생성 → 반영 완료 → 키 발급 원문 확인 → 닫기 → 폐기.
- 두 개의 환경을 등록한 뒤 두 번째를 선택한다. 설정 저장·새로고침·키 폐기 후에도 두 번째 환경이 선택되어 있어야 한다.
- 중지 후 환경 생성·키 발급 버튼이 비활성화되고 재개 후 돌아오는지 확인한다. 기존 폐기 키는 그대로 폐기 상태여야 한다.
- 콜백을 변경한 뒤 변경 값과 가입 상태가 화면에 반영되는지 확인한다.
- 390px 폭에서 본문 가로 넘침이 없고 개발·운영 모드 표시가 보이는지 확인한다. 모바일에서 설정 저장도 수행한다.
- 밝은 테마 전환 후 새로고침해 선택이 유지되는지 확인하고 어두운 테마도 확인한다.
- 대화상자에서 Tab·Shift+Tab이 내부 컨트롤을 순환하고 Escape로 닫은 뒤 실행 버튼으로 포커스가 돌아오는지 확인한다.
- 브라우저 개발자 도구에서 정상 동작 중 JavaScript 오류가 없는지 확인한다. 비밀번호·토큰·키 원문을 콘솔, 스크린샷, 공유 기록에 남기지 않는다.

개발 중 Playwright CLI로 이 흐름을 실제 Chromium에서 검증했다. 캡처는 로컬 `output/playwright/`에 저장하며 Git에서 제외한다. 테스트 전용 `browser-check-0925` 프로젝트가 개발 DB에 남아 있고 발급한 검사 키는 폐기한다. Windows 브라우저와 실제 모바일 기기 테스트는 별도다.

## 가입·계정 복구 정책

환경의 **가입·계정 복구**에서 이메일 로그인, 이메일 인증 필수 여부, 이메일로 비밀번호 재설정 허용, 비밀번호 최소 길이를 저장한다. 일반 회원가입 허용은 위쪽 **로그인 설정 → 설정 변경**에서 계속 관리한다. 각 설정은 현재 환경에만 적용된다.

- 기존 계정·비밀번호·현재 세션은 바꾸지 않는다. 새 환경의 비밀번호는 기본 12~128자이며, 최소 길이를 12~128에서 정할 수 있다. 기존 환경에 최소 길이가 없으면 안내를 표시하며 저장 전에는 기존 동작을 유지한다.
- 이메일 인증을 켜면 아직 인증하지 않은 기존 사용자도 다음 로그인에서 확인을 요구받을 수 있다. 비밀번호 재설정은 Keycloak 로그인 화면의 비밀번호 찾기를 사용한다. 소셜 제공자 비밀번호와 플랫폼 관리자 계정 복구는 별개다.
- 이메일 발송 설정이 없는 환경이나 개발 모드·DEV에서는 이메일 인증·재설정을 켤 수 없다. NCP 발송 연동과 개발 모의 수신함이 준비된 뒤 실제 발송·복구를 검수한다. 발송 설정의 존재가 발송 성공을 뜻하지 않는다.
- Keycloak에서 별도로 설정한 비밀번호 규칙은 덮어쓰지 않도록 편집을 막는다. 기존 규칙을 먼저 검토해야 한다. 저장 충돌·실패가 나면 **정책 새로고침**으로 현재 값을 확인한다.

정책을 저장하는 것만으로 이메일을 발송하지 않는다. 프로젝트 중지 중에도 정책은 편집할 수 있지만 로그인이 허용되는 것은 아니다.

## 소셜 로그인 설정

환경의 **소셜 로그인**에서 카카오·네이버·구글을 선택한다. 인증 정보가 없어도 등록할 콜백 주소와 제공자별 공식 안내를 확인할 수 있다. 현재 실제 인증 정보 입력과 외부 로그인 검수는 사용자 요청으로 보류했다.

1. 소셜 개발자 콘솔에서 현재 환경에 표시되는 콜백 URL을 추가한다. 기존 서비스의 키·콜백을 삭제하거나 덮어쓰지 않는다. 운영에서는 `https://platform.shnea.kr/auth/realms/.../broker/.../endpoint` 형태다. 개발 화면의 localhost 주소를 운영 콜백으로 사용하지 않는다.
2. 카카오는 OpenID Connect를 켜고 REST API 키·활성화한 Client Secret을 입력한다. 네이버는 Client ID·Client Secret, 구글은 웹 애플리케이션 OAuth 클라이언트 ID·보안 비밀번호를 입력한다. 동의 항목·앱 검수·도메인 등록은 각 제공자의 콘솔에서 별도로 관리한다.
3. **소셜 설정 저장**을 누른다. 기존 앱 키를 유지하면서 비밀키를 비우면 기존 비밀키가 유지된다. 앱 키가 바뀌면 새 앱의 비밀키를 함께 입력한다. 비밀키 입력은 요청 시 지우며 이후 조회하지 않는다. 제공자/환경 이동·설정 새로고침도 미저장 입력을 지운다.
4. 실제 로그인은 운영 모드의 PROD 환경에서 **실제 로그인에서 사용**으로 활성화한다. DEV·개발 모드는 기존 Mock을 사용한다. 프로젝트가 중지 상태면 설정을 켜도 realm이 비활성 상태여서 로그인할 수 없다.
5. 저장 상태는 **미설정 / 사용 안 함 / 사용 중**으로 표시한다. ‘사용 중’은 설정 값이며 연결 성공 판정이 아니다. 실제 로그인·동의 거부·콜백 오류·프로젝트 격리 검수는 인증 정보 보강 후 진행한다.

저장 충돌·실패 시 **설정 새로고침**으로 현재 값을 확인한 뒤 다시 저장한다. 응답을 받지 못해도 Keycloak에 이미 반영되었을 수 있다. 콜백 주소는 선택하면 전체를 선택할 수 있으며 복사 후 외부 콘솔에 등록한다. 위쪽 **로그인 설정 → 콜백 URL**은 플랫폼에서 연결 서비스로 복귀할 주소이므로 두 종류의 콜백을 구분한다.

## 개발 로그인 테스트

개발 모드에서 프로젝트의 DEV 환경을 선택하면 **개발 로그인 테스트**가 나타난다. 카카오·네이버·구글, 테스트 사용자 ID, 성공·로그인 취소·동의 거부·제공자 장애 중 하나를 선택하고 **테스트 실행**을 누른다. 프로젝트가 사용 중이고 환경 설정이 반영 완료여야 한다. PROD에는 표시하지 않는다.

관리자 로그인으로 검사하므로 서버 API 키를 입력하지 않는다. 성공하면 내부 Keycloak에 테스트 사용자·세션을 만들고 사용자 식별자·발급자·토큰 유효기간을 표시한다. 화면과 관리자 응답에는 토큰 원문이 없다. 실패 재현에서는 사용자를 변경하거나 토큰을 발급하지 않는다. 표시된 HTTP 상태는 연동용 Mock API의 응답 상태이며 실제 실행 장애는 오류 안내로 구분한다.

입력을 바꾸거나 환경을 이동하면 이전 결과를 지운다. **결과 지우기**는 화면 결과만 지우며 테스트 사용자·세션·감사 기록을 삭제하지 않는다. 실행 도중 환경을 바꿔도 이미 서버에 전달한 검사가 취소되지는 않는다. 실제 소셜 서비스 연동·리다이렉트·콜백 확인은 별도 검수 대상이다.

## 배포와 제한

웹 이미지 `register.shnea.kr/platform-admin-web:태그`는 React·TypeScript·Vite 빌드 결과를 제공한다. `compose.yml`만 사용하는 운영에서는 소스 마운트가 없으며 30140의 Nginx를 통해 접속한다. 메모리·CPU는 `ADMIN_WEB_MEMORY`, `ADMIN_WEB_CPUS`로 조정한다.

`PLATFORM_WEB_URL`은 경로 없는 정확한 origin이다. 개발 기본값은 `http://localhost:30140`, 운영 값은 `https://platform.shnea.kr`이다. 운영 `KEYCLOAK_PUBLIC_URL`은 `https://platform.shnea.kr/auth`로 설정한다. 변경 후 `identity-setup`을 다시 실행하면 관리자 로그인·로그아웃 콜백이 `https://platform.shnea.kr/`로 등록된다. IP 주소로 임의 접속하면 허용된 콜백과 달라 로그인할 수 없다. 실제 DNS·TLS 배포는 아직 검증하지 않았다.

발급 창의 **사용 권한**은 **연동 정보 조회**만 기본 선택한다. DEV 환경에서 가짜 로그인이 필요하면 **개발용 가짜 로그인**을 추가로 선택한다. PROD 환경에서는 해당 항목을 제공하지 않는다. 하나 이상의 권한을 선택해야 하며 키 목록에서 발급된 권한을 확인할 수 있다. 권한을 변경하려면 새 키를 발급해 연결 서비스를 전환한 뒤 기존 키를 폐기한다. 권한 목록을 불러오지 못하면 발급을 막고 오류를 표시하므로 새로고침 후 다시 시도한다.

현재 화면은 플랫폼 관리자용이다. 초대·소셜별 가입 정책, NCP 이메일 발송·실제 복구 검수, 관리자 MFA 설정, 파일·알림별 키 권한, 사용량·파일·알림·에디터 관리 화면은 아직 없다. Keycloak 자체 로그인 화면은 기본 테마를 사용한다. 운영 모드 브라우저 설정 코드는 있으나 실제 운영 TLS 배포·운영 사용자 로그인 검증을 완료한 것은 아니다.
