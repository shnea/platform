# 공통 서비스 관리 플랫폼 요구사항 정의서

- 작성일: 2026-09-25
- 버전: 0.12 — 개발 기반 확정 및 에디터 Markdown 붙여넣기 필수 반영
- 상태: 주요 기능과 개발·배포 제약을 합의했다. 남은 상세 정책·버전·검증 수치는 구현 단계에서 구체화한다. 현재 문서 정리 단계이며 기능 구현 완료를 뜻하지 않는다.
- 표기: **확정**은 사용자가 명시한 내용, **제안**은 검토할 기본안, **미정**은 결정이 필요한 내용이다.
- 이 문서는 요구사항을 정리한다. 구현 착수나 모든 제안의 채택을 의미하지 않는다.

## 1. 목적

### 확정

현재 별도로 운영하는 로그인/IdP, 파일, 알림 기능을 새롭게 구현하고, 하나의 관리자 화면에서 관리하는 공통 서비스 플랫폼을 만든다. 앞으로 만드는 여러 프로젝트가 사용법과 연동 예제를 참고해 쉽게 연결할 수 있어야 한다.

공통 블록 에디터와 읽기 전용 뷰어도 제공한다. 플랫폼은 여러 프로젝트에서 사용하는 공통 기능과 UI 컴포넌트, 이를 위한 통합 관리 기능을 제공한다.

기존 저장소는 필요한 기능과 경험을 확인하는 참고 자료다. 기존 서비스 코드를 재사용하거나 기존 서비스 화면만 묶는 방식으로 구현하지 않는다.

새 플랫폼은 앞으로 추가되는 프로젝트에만 적용한다. 현재 운영 중인 기존 서비스와 연결 프로젝트는 그대로 유지하며, 이전·교체·종료 작업은 이번 요구사항에 포함하지 않는다.

| 기존 서비스 | 참고 저장소 | 현재 확인 수준 |
|---|---|---|
| 로그인/IdP | http://git.shnea.kr/shnea/login.git | Git 읽기 접근 확인, 내부 기능·API 미검토 |
| 파일 | http://git.shnea.kr/shnea/file-service.git | Git 읽기 접근 확인, 내부 기능·API 미검토 |
| 알림 | http://git.shnea.kr/shnea/notify.git | Git 읽기 접근 확인, 내부 기능·API 미검토 |

### 제안하는 성공 기준

- 새 프로젝트가 플랫폼 소스를 수정하지 않고 설정과 공개된 연동 방법만으로 필요한 기능을 사용한다.
- 관리자가 프로젝트, 사용자 접근, 파일, 알림 처리 결과와 주요 이력을 한곳에서 확인하고 조치한다.
- 프로젝트별 데이터와 권한을 분리하고 공통 기능의 중복 개발을 줄인다.
- 새 구현에서도 표준 라이브러리·검증된 인증 구성요소·오픈소스 사용은 허용하는 것으로 제안한다. 직접 구현할 범위는 7절에서 확정한다.

## 2. 사용자

### 확정

- 주 운영자·개발자는 본인이다.
- 앞으로 개발하는 다수의 서비스에서 공통 기능을 사용하는 것이 목표다.
- 연결된 서비스의 최종 이용자는 불특정 다수가 될 수 있다.
- 프로젝트마다 회원과 로그인을 완전히 분리한다. 프로젝트 간 통합 계정·SSO를 제공하지 않는다.
- 동일한 이메일/아이디를 사용하는 사람이 여러 프로젝트에 가입해도 별도 계정으로 취급한다. 비밀번호 변경·계정 정지·삭제·세션은 해당 프로젝트 범위에서 동작한다.
- 가입 방식은 프로젝트별로 허용·설정한다. 제공할 구체적인 가입 방식과 세부 동작은 아래 기능 요구에서 정한다.

### 제안하는 역할 구분

| 역할 | 주요 행동 | 접근 범위 |
|---|---|---|
| 플랫폼 관리자 | 프로젝트 등록, 설정, 자격증명 관리, 운영 상태 확인 | 플랫폼 관리 권한 |
| 연동 개발자 | 사용법 확인, 개발 환경 연결, 오류 확인 | 본인이 관리하는 프로젝트; 초기에는 관리자와 동일인 |
| 연동 서비스 | 인증 연동, 파일 처리, 알림 요청 | 발급받은 프로젝트·환경·기능 권한 |
| 최종 이용자 | 서비스에서 로그인, 허용된 파일 이용, 알림 수신 | 자신의 서비스 이용 권한; 관리자 화면 접근 불가 |

‘프로젝트’는 플랫폼에 연결하는 개별 서비스를 뜻한다. ‘환경’은 개발·검증·운영 구분이다. 여러 고객 조직을 관리하는 별도 테넌트 체계는 아직 요구하지 않는다.

### 미정

- 일반 회원가입, 초대 가입, 관리자 생성 등 프로젝트별로 선택할 가입 방식의 상세 목록.
- 향후 본인 외 관리자에게 프로젝트별 관리 권한을 위임할지.
- 프로젝트 안에서도 개발·운영 환경의 회원을 분리하는 것을 제안한다. 이는 확정된 프로젝트 간 분리에 추가하는 환경 정책이다.

## 3. 핵심 기능

로그인/IdP·파일·알림 6개 채널·에디터/뷰어·개발 모의 연동을 첫 출시부터 제공한다. 기능별 독립 사용, 연동 확인 화면과 실행 예제, 사용량·실패·삭제 예정 현황, 이벤트 웹훅도 **첫 출시 필수 범위로 확정**한다. 상세 구현 제안은 확정 요구와 구분한다.

| ID | 기능 | 제안하는 1차 범위 | 우선순위 |
|---|---|---|---|
| F-01 | 프로젝트·환경 관리 | 프로젝트 생성·조회·중지, 환경 구분, 기능 설정, 허용 출처·콜백 관리 | 1차 필수 |
| F-02 | 로그인/IdP | 카카오·네이버·구글 로그인, 가입 정책, 로그인·로그아웃, 사용자 상태, 계정 복구, 세션 관리, 표준 인증 연동 | 소셜 3종 요구 확정; 나머지 상세 정책은 제안 |
| F-03 | 서비스 자격증명 | 프로젝트·환경·권한을 제한한 자격증명 발급·교체·폐기 | 1차 필수 |
| F-04 | 파일 서비스 | 최대 5GB, 멀티·드래그·분할 업로드, 일시정지·재개, 용도별 URL, 보존 정책 코드, 접근 제어 | 상세 요구는 아래 참조 |
| F-05 | 알림 서비스 | 이메일·앱 내 알림·웹 푸시·SMS·카카오·Telegram 6개 채널, 템플릿·변수, 발송 요청, 처리 상태, 실패 원인, 재시도 | 6개 채널 1차 필수 확정; 세부 동작은 제안 |
| F-06 | 감사 로그 | 주요 관리 작업과 보안 이벤트의 주체·대상·시간·결과 조회 | 1차 필수 |
| F-07 | 운영 상태·로그 | 플랫폼 상태, 오류, 요청 식별자, 실패 작업 확인 | 1차 필수 |
| F-08 | 통합 관리자 화면 | 위 기능의 조회·설정·조치, 프로젝트·환경별 검색과 필터 | 1차 필수 |
| F-09 | 개발자 연동 안내·검증 | 시작 안내, API 명세, 인증 설정, 환경변수 예시, 연동 확인 화면, 실행 가능한 예제 | 첫 출시 필수 확정 |
| F-10 | 사용량·운영 현황 | 프로젝트별 파일 용량·발송량, 미완료 업로드·발송 실패·삭제 예정 파일, 상한 설정 | 현황 첫 출시 필수 확정; 상세 집계 정책은 설계 |
| F-11 | 공통 블록 에디터·뷰어 | 슬래시 명령, 서식, 파일 첨부, 이미지 나란히 배치, 드래그, 모바일, React·Vue·일반 JS 연동 | 첫 출시 필수 확정 |
| F-12 | 개발 모의 연동 | 개발 환경에서 외부 인증·발송 없이 테스트 계정과 가상 결과로 핵심 흐름 실행 | 요구 확정; 환경변수 이름·세부 구현 미정 |
| F-13 | 이벤트 웹훅 | 미리보기 생성·알림 상태 변경 등을 프로젝트가 등록한 수신 주소로 전달 | 첫 출시 필수 확정 |

기능별 독립 사용은 전체 기능의 공통 요구다. 로그인·파일·알림 중 필요한 기능만 연동할 수 있어야 하며, 에디터는 자체 업로드 연결을 사용하면 플랫폼 계정이나 서버 연결 없이 사용할 수 있어야 한다. 파일·알림 API 사용에 필요한 프로젝트 인증은 최종 이용자의 플랫폼 로그인과 구분한다.

### 기능별로 정할 사항

- **F-02:** 카카오·네이버·구글 로그인은 포함한다. 이메일/아이디·비밀번호 로그인, 관리자 MFA 및 복구 방법은 상세 정책을 정한다. 프로젝트 사이에서 플랫폼 계정·세션을 공유하지 않는다. 플랫폼 관리자 계정도 서비스 이용자 계정과 구분한다.
- **F-03:** 최종 사용자 인증과 서버 간 인증을 구분한다. 서버용 비밀키를 브라우저에 배포하지 않는다. 교체 중 유예 기간과 폐기 효력 발생 시점을 정의한다.
- **F-04:** 기본 공개로 URL을 아는 누구나 파일을 볼 수 있다. 별도로 비공개·비밀번호 보호 공유를 지원한다. 업로드·목록·수정·삭제·설정 권한은 공개 조회와 구분한다. 보존 정책 코드의 기간 변경은 해당 코드를 사용하는 기존 파일에도 적용한다.
- **F-05:** 이메일·앱 내 알림·웹 푸시·SMS·카카오·Telegram을 모두 1차에 제공한다. 큐에 접수된 상태와 외부 제공자가 수락한 상태, 실제 전달 확인 상태를 구분한다. 제공자가 확인하지 않는 실제 수신 여부는 성공으로 단정하지 않는다.
- **F-06:** 일반 관리 기능에서 감사 기록을 임의로 수정·삭제할 수 없게 하고 보존 기간을 정한다. 시스템 최고 권한까지 막는 변조 방지 저장소는 별도 요구로 판단한다.
- **F-07:** 플랫폼 자체 진단을 우선한다. 연결된 모든 서비스의 로그를 수집·분석하는 범용 시스템은 별도 후보로 둔다.

### 소셜 로그인 상세 — F-02

**확정 요구:** 카카오·네이버·구글 로그인 지원. 사용자는 이미 사용하는 소셜 앱이 있으며 새 URL을 추가하는 방식을 검토하고 싶어 한다. 기존 앱 설정은 아직 확인하지 않았다.

**제안 및 확인 사항:**

- 플랫폼 관리 화면에서 프로젝트·환경별 제공자 사용 여부, 클라이언트 설정, 필요한 콜백 주소와 연결 상태를 관리한다.
- ‘소셜 제공자에서 플랫폼으로 돌아오는 콜백’과 ‘플랫폼 인증 후 각 프로젝트로 돌아가는 콜백’을 구분한다. 외부 콘솔 등록은 제공자별 요구사항에 따라 필요하며 플랫폼 화면만으로 자동 등록된다고 가정하지 않는다.
- 기존 소셜 앱을 함께 사용할 수 있는지는 앱의 서비스 범위·도메인·동의 항목·등록 제한·검수 상태를 확인한다. 독립 프로젝트는 외부 소셜 앱도 분리하는 안을 우선 검토한다. 기존 콜백·키를 덮어쓰지 않는다.
- 동일한 외부 소셜 계정을 사용해도 플랫폼 회원은 프로젝트별로 생성한다. 이메일만으로 기존 계정을 자동 병합하지 않는다.
- 플랫폼 계정 분리와 소셜 제공자의 로그인 세션은 별개다. 제공자에 이미 로그인되어 있으면 다시 비밀번호를 입력하지 않을 수 있으며, 이를 프로젝트 간 플랫폼 계정 공유로 해석하지 않는다.
- 프로젝트 탈퇴 시 공유된 소셜 앱의 연결 해제·동의 철회가 다른 서비스에 영향을 주는지 확인한다. 연결 앱을 공유한다면 프로젝트 탈퇴와 외부 제공자 연결 해제를 분리한다.
- 인증 엔진은 Keycloak으로 확정했다. 카카오·네이버별 프로토콜 지원과 어댑터 필요성을 검증하며 모든 제공자가 기본 설정만으로 연결된다고 가정하지 않는다.

등록 방식 참고: [카카오 로그인 설정](https://developers.kakao.com/docs/ko/kakaologin/prerequisite), [네이버 로그인 가이드](https://developers.naver.com/docs/login/devguide/devguide.md), [구글 OAuth 웹 서버 가이드](https://developers.google.com/identity/protocols/oauth2/web-server).

### 파일 형식·URL·뷰어 — F-04

**확정 요구:** TXT·PDF·MD 등 문서, MP3·MP4 등 미디어, PNG·JPG 등 이미지를 포함해 대부분의 형식을 업로드할 수 있어야 한다. 이미지 미리보기, 원본 보기, 다운로드, 카카오톡 등에서의 OG 미리보기를 위한 URL을 제공한다.

멀티 업로드와 드래그 앤 드롭 업로드는 **필수**다. 여러 파일을 선택하거나 끌어 놓아 업로드할 수 있어야 한다. 폴더 전체 업로드는 아직 요구하지 않았다.

최대 업로드 크기는 **5GB**로 지정되었다. 파일당 상한으로 해석해 반영하며 정확한 바이트 기준은 아래 제안과 같다. **분할 업로드·일시정지·이어서 업로드**를 추가 요구로 포함한다.

**업로드 UX 제안:**

- 공통 업로더와 에디터에서 같은 파일 처리 계약을 사용한다. 모바일·키보드 사용자는 파일 선택 버튼으로 여러 파일을 추가할 수 있다.
- 파일별 대기·업로드 중·일시정지·재연결 대기·검증 중·완료·실패·취소·만료 상태와 진행률을 표시한다. 원본 업로드 완료와 미리보기 변환 중 상태를 구분한다.
- 일부 파일이 실패하면 성공한 결과를 보존하고 실패한 파일만 재시도한다. 취소가 이미 완료된 파일의 삭제를 뜻하지 않게 한다.
- 동일한 이름의 파일도 구분할 수 있는 요청 항목 식별자를 사용한다. 요청 재시도로 같은 파일이 의도치 않게 중복 생성되는 경우를 처리한다.
- 초기 파일당 상한은 5GB로 적용하고 파일 수·요청 총량·업로드 동시 처리 수의 제한은 별도로 설정 가능하게 한다. 초과 원인을 표시한다. 바이트 기준은 5,000,000,000 bytes를 제안하며 API와 화면이 같은 기준을 사용한다.

**분할·재개 상세 제안:**

- 파일별 업로드 세션을 발급하고 브라우저에서 작은 단위로 나눠 전송한다. 서버가 수신 완료한 위치 또는 조각 목록을 기준으로 남은 데이터만 보낸다.
- 일시정지하면 추가 전송을 멈추고 이미 수신한 데이터는 유지한다. 재개 시 서버의 확정 상태를 확인하며, 중단 당시 전송 중이던 부분은 필요하면 다시 보낸다.
- 네트워크 단절은 제한된 재시도와 재연결 대기로 처리한다. 인증 만료 시 재인증 후 소유권을 확인해 이어 올린다.
- 페이지 새로고침·브라우저 재접속 이후에도 만료되지 않은 업로드 세션을 조회해 재개할 수 있게 한다. 원본 파일 접근 권한이 사라진 경우 사용자에게 같은 파일을 다시 선택하도록 안내한다. 이름만으로 동일 파일을 판정하지 않는다.
- 서버 재시작 후에도 세션과 수신 데이터가 유지되도록 한다. 세션은 프로젝트·환경·사용자에 귀속시키고 조회·전송·완료·취소 모두 권한을 검증한다.
- 조각의 중복 전송·누락·길이 불일치·손상을 처리하고 최종 파일 크기와 무결성을 검증한다. 여러 탭의 동시 재개나 완료 요청 재시도로 파일이 중복 생성되지 않게 한다.
- 분할 전송이 5GB 제한을 우회하지 않도록 선언 크기와 실제 누적 수신량을 서버에서 확인한다. 프로젝트 용량·진행 중 업로드·임시 조각도 저장 공간 사용량에 반영한다.
- 브라우저와 서버가 5GB 전체를 한 번에 메모리에 적재하지 않도록 한다. 조각 크기·동시 처리·프록시 요청 크기·타임아웃을 함께 검증한다.
- 파일 내용 검증과 최종 확정 이후에 완료 파일로 노출한다. 완료 요청과 결과 조회는 재시도 가능하게 하고 URL 응답은 기존 파일 결과 구조로 통일한다.
- 미완료 업로드 세션의 보관 기간·일시정지 중 만료·취소 정리는 별도 설정으로 관리한다. 이는 완료 파일의 보존 정책과 구분하며 만료 시각을 사용자에게 표시한다.
- 에디터는 문서 본문이나 원본 파일을 로컬에 영속 저장하지 않는다. 재개는 파일 서비스의 업로드 세션과 사용자가 제공한 원본 파일을 이용하며 호스트 서비스에 연동 방법을 제공한다.
- 구현 시 tus 등 기존 재개 프로토콜과 선택한 저장소의 분할 업로드 기능을 먼저 검토한다. 특정 프로토콜·라이브러리는 아직 확정하지 않는다. [tus 재개 업로드 명세](https://tus.io/protocols/resumable-upload)

**업로드 응답 방향 — 사용자 예시를 참고한 제안:**

사용자는 기존 서비스가 `message`와 `files` 배열을 반환하고 각 파일에 `originalname`, `fileId`, `previewUrl`, `downloadUrl`, `shareUrl`을 제공한다고 설명했다. 이 형태를 참고하되 기존 필드명·경로·도메인과의 완전 호환은 요구하지 않았다.

- 파일별 식별자와 용도별 URL을 반환하는 구조를 유지하는 방향으로 설계한다. 원본 URL도 추가한다.
- 파일명은 `originalName` 등 일관된 이름을 사용하고 형식·크기·미리보기 상태를 제공한다. 실제 응답 필드명은 API 설계에서 확정한다.
- 보존 정책 코드와 적용된 기간/영구 여부, 최근 이용 시각, 현재 계산된 자동 삭제 대상 시각을 제공하는 안을 제안한다. 자동 삭제 대상 시각은 이용에 따라 바뀔 수 있으며 URL 만료 시각과 구분한다.
- 성공은 `files`, 실패는 `errors` 등으로 파일별 결과를 구분하고 요청 항목 식별자로 대응시킨다. 사람이 읽는 `message`를 파싱해 성공 여부를 판단하지 않는다.
- 실패 항목에는 원본 이름·오류 코드·설명·재시도 가능 여부를 제공한다. 미리보기 미지원/변환 대기 파일을 업로드 실패로 취급하지 않는다.
- 비공개 파일의 URL은 인증된 접근 또는 만료 링크 정책을 따른다. 파일 ID로 URL을 재조회할 수 있게 한다.

**공개·비공개·공유 — 확정 요구와 상세 제안:**

- 기본 파일은 공개이며 URL을 알면 로그인 없이 조회할 수 있다. 공개 조회를 허용해도 프로젝트 전체 파일 목록·관리 작업까지 공개하지 않는다.
- 비공개와 별도 공유 기능을 제공한다. 비밀번호 입력 후 보기 방식을 포함하며, 공유 링크별 만료·철회·접근 범위 설정은 상세 제안으로 둔다.
- 비공개 전환 또는 공유 철회 후 `previewUrl`·`originalUrl`·`downloadUrl`로 보호를 우회하지 못하게 한다. 원본·미리보기·파생 파일과 캐시 정책을 함께 처리한다.
- 비밀번호는 안전하게 저장하고 URL에 포함하지 않는다. 성공한 비밀번호 확인 후 공유 범위에 한정된 접근 수단을 제공하며 실패 시도 제한을 적용한다.
- 비공개·비밀번호 보호 파일의 OG에는 기본 안내만 표시하는 것을 제안한다. 공개 파일도 제목·대표 이미지 등 OG 표시 범위를 설정할 수 있게 한다.

**지원 범위 제안:** 업로드·원본 보관은 폭넓게 지원하고, 미리보기 가능한 형식을 명시한다. 브라우저의 미디어 지원은 형식과 코덱에 따라 다르다. [MDN 미디어 형식 안내](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats)

| 구분 | 기본 제공안 | 별도 범위 확인 |
|---|---|---|
| 일반 이미지 | 작은 미리보기와 원본 확대 | HEIC·RAW·대형 애니메이션 등의 변환 |
| TXT·MD·PDF | 텍스트·안전하게 렌더링한 Markdown·PDF 보기 | 대용량·암호화·손상 문서 처리 |
| 오디오·영상 | 지원 형식 재생, 영상 대표 이미지, 원본 다운로드 | 전체 코덱 변환·영상 저화질 스트리밍 |
| Office·HWP·기타 | 원본 보관·다운로드, 파일 정보 카드 | 각 형식의 내용 미리보기·변환 |

- `previewUrl`, `originalUrl`, `downloadUrl`, `shareUrl`처럼 용도가 구분되는 URL 계약을 제공하는 안을 제안한다. 미지원 형식은 미리보기 가능 여부와 대체 동작을 반환한다.
- `shareUrl`은 OG 태그가 있는 HTML 페이지다. 이미지 URL 자체와 구분한다. 비공개 파일은 기본적으로 일반 안내 이미지·제목만 공개하고 실제 내용은 인증 후 연다. 내용이 보이는 공유 미리보기는 명시적으로 허용한 범위만 공개한다.
- 카카오 서버가 읽을 공개 메타데이터와 대표 이미지가 필요하며 외부 캐시가 남을 수 있다. 공유 철회 후 플랫폼의 접근은 막되 외부에 이미 저장된 미리보기의 즉시 소거를 보장하지 않는다. [카카오 OG 캐시 안내](https://developers.kakao.com/docs/ko/message-template/faq)
- 기본 파일 뷰어를 선택적으로 제공한다. 작은 미리보기를 먼저 로딩하고 사용자 동작 시 원본·상세 보기를 연다. 서비스는 URL만 사용하거나 자신의 뷰어로 교체할 수 있다.
- 임의 HTML·SVG·스크립트를 플랫폼과 같은 신뢰 영역에서 실행하지 않는다. 파일명·형식 검사, 안전한 다운로드 응답, 콘텐츠 렌더링 격리와 필요한 검사 범위를 정한다.
- 원본 보관과 미리보기 생성 상태를 구분한다. 변환 작업은 요청 처리와 분리하고 시간·동시 처리·입력 크기를 제한한다. 전체 영상을 저용량으로 변환하는 기능은 사용자 확인 없이 필수 범위로 확장하지 않는다.

### 파일 수명주기 — F-04

**확정 요구:** 고정 제공하는 보존 코드는 `default`, `tmp`, `영구` 세 개뿐이다. 그 외 코드는 관리자가 직접 등록하면서 기간을 지정한다. 코드 목록을 열거형으로 고정하지 않는다.

| 고정 코드 | 초기 설정 |
|---|---|
| `default` | 1년 미사용 삭제; 업로드 시 코드 생략하면 적용 |
| `tmp` | 1일 미사용 삭제 |
| `영구` | 미사용 기간에 따른 자동 삭제 없음 |

`week`, `month`, `year`, `2year`는 고정 코드나 기본 생성 목록이 아니다. 필요하면 관리자가 다른 임의 코드와 마찬가지로 등록한다. 예를 들어 `archive`라는 코드를 만들면서 기간을 2개월로 지정할 수 있으며, 코드 이름과 기간은 독립적으로 관리한다.

**정책 관리 제안:**

- 업로드 시 보존 정책 코드를 선택하고 생략하면 기본 정책을 적용한다. `default`의 초기 기간은 1년이다.
- 코드 등록 화면에서 코드·표시 이름·기간 값·단위를 입력한다. 코드 문자열을 보고 기간을 추측하지 않는다. 코드와 기간 값·단위 또는 영구 여부를 별도 설정으로 관리한다. 고정 3개 외의 미등록 코드는 오류로 안내한다.
- 앞서 합의한 ‘최근 조회·호출로부터 미사용 기간’ 기준을 유지한다. `tmp`도 우선 같은 기준으로 해석하며, 업로드 후 고정 기간 만료가 필요하면 별도 정책으로 정의한다.
- 사용자 코드 추가·기간 수정·사용 중지와 파일별 정책 변경을 지원하는 안을 제안한다. 고정 코드와 사용자 등록 코드의 관리 범위를 구분한다. 영구 보존도 권한 있는 명시적 삭제는 가능하며, 자동 만료만 제외한다.
- **확정:** 코드의 기간을 변경하면 해당 코드를 참조하는 기존 파일에도 적용한다. 업로드 당시 기간으로 기존 파일을 고정하지 않는다.
- **구현 제안:** 파일은 정책 코드를 참조하고 현재 정책·최근 이용 시각으로 삭제 대상 시각을 계산한다. 기간 단축·연장 모두 조회와 삭제 작업에 반영하고, 최종 삭제 직전에 최신 정책을 확인한다. 변경 전후 값은 감사 이력으로 남긴다.
- 기간 단축으로 기존 파일이 삭제 대상이 되는 경우 관리자에게 영향과 대상 수를 표시하는 것을 제안한다. 적용된 정책에 따른 삭제 작업은 합의한 실행 주기·유예에 따라 처리한다.
- 사용 중인 코드를 삭제할 때 연결된 파일의 정책이 유실되지 않게 한다. 공개 범위와 보존 기간은 서로 독립된 설정이다.

**결정이 필요한 상세 정책 및 제안:**

- 최초 기준은 업로드 완료 시각, 이후에는 성공한 콘텐츠 이용 시각을 사용하는 안을 제안한다. 미리보기·원본·다운로드의 이용을 같은 원본 파일의 사용으로 집계한다.
- 목록·상태 조회·실패 요청·내부 변환 작업이 보존 기간을 계속 연장하지 않도록 구분한다. OG 봇 호출·공개 링크 접근의 포함 여부와 ‘1년’의 계산 기준을 확정한다.
- 브라우저·CDN 캐시에서 제공된 조회는 원본 서버에 도달하지 않을 수 있다. 서버/캐시 로그와 필요한 이용 이벤트를 기준으로 집계하고 미집계 구간의 처리 정책을 정한다.
- 장기 보관이 필요한 첨부는 연결 서비스가 영구 또는 적절한 기간의 정책을 선택한다. 에디터가 자동으로 영구 정책을 선택하거나 외부 문서 참조를 추적하는 동작은 기본 범위로 추가하지 않는다.
- 삭제 예정 목록·감사 기록·설정 가능한 복구 유예를 제안한다. 최종 삭제 직전에 최근 이용·보존 예외를 다시 확인하고, 원본·파생 미리보기·공유 URL의 처리 상태를 일치시킨다.
- 복구 유예와 백업에 남는 기간은 최종 삭제 정책에 명시한다. 문서에서 첨부를 제거한 즉시 원본을 삭제하지 않는다.

### 블록 에디터·뷰어 — F-11

**확정 요구:**

- 노션과 같은 블록 편집 방식, `/image`·`/file` 등 슬래시 명령.
- 폰트, 이모지, 제목, 들여쓰기 등 편의 기능. 구체적인 전체 목록은 추가 합의한다.
- 한 줄에 이미지 2개 배치, 드래그 앤 드롭 삽입·이동, 모바일에서 자연스러운 편집과 읽기.
- 여러 서비스의 디자인에 맞춰 사용할 수 있는 에디터와 읽기 전용 뷰어 제공.
- 기본 업로드는 플랫폼 파일 서비스 사용, 필요하면 각 서비스의 업로드 방식으로 교체 가능.
- React·Vue·일반 HTML/JavaScript와 JSP 페이지에서 사용 가능.
- 에디터 본문은 각 서비스가 저장한다. 에디터와 플랫폼은 본문 저장 기능을 제공하지 않으며 데이터 입출력·변경 이벤트·사용법과 연동 예제를 제공한다.
- 에디터의 파일 첨부에서도 멀티 업로드·드래그 앤 드롭을 지원한다.
- 에디터와 뷰어는 첫 출시부터 제공한다.
- Markdown 문서 내용을 복사해 붙여넣으면 구조와 서식이 올바른 에디터 블록으로 변환·렌더링되어야 한다. 첫 출시 필수 기능이다.

**설계 제안:**

- 하나의 편집 코어·문서 형식·공통 UI를 만들고 React·Vue 연결 코드는 얇게 유지한다. 일반 JS는 `mount`·값 읽기/쓰기·변경 이벤트·`destroy` 형태로 제공한다. JSP는 생성한 HTML에서 일반 JS 번들을 로딩한다.
- Tiptap/ProseMirror 기반을 우선 후보로 둔다. Tiptap은 React·Vue·일반 JS 통합을 지원하지만 노션형 메뉴·레이아웃·드래그 UI는 별도로 구현할 부분이 있다. React 기반 BlockNote도 비교 후보이나 여러 프레임워크 배포에서 React 런타임 포함 여부를 고려한다. [Tiptap](https://tiptap.dev/docs/editor/getting-started/overview), [BlockNote](https://www.blocknotejs.org/docs/getting-started)
- 라이브러리 버전·라이선스·유료 확장 의존 여부를 기능별로 확인한 뒤 채택한다. 모든 고급 기능이 기본 제공이라고 가정하지 않는다.
- 기본 테마는 중립적으로 두고 글꼴·색·간격·테두리 등 제한된 디자인 설정을 제공한다. 서비스의 전역 CSS와 에디터 스타일이 서로 침범하지 않도록 한다.
- 에디터는 버전이 있는 JSON 문서 데이터를 입력·출력하고 뷰어와 같은 블록 정의를 사용한다. 저장은 호스트 서비스가 수행한다. HTML·Markdown 내보내기는 선택 기능이며 이미지 열 배치 등 서식이 손실될 수 있음을 명시한다.
- 파일 노드에는 만료 URL만 저장하지 않고 저장 제공자와 안정적인 파일 식별자를 둔다. 조회 시 URL을 다시 얻는 계약을 제공한다. 자체 업로드로 교체하면 미리보기·권한·보존 기능 중 어느 부분을 외부 서비스가 담당하는지 명시한다.
- 업로드 연결 계약에는 진행 상태·취소·실패·재시도, 파일 정보, 원본/미리보기 URL 조회를 포함한다. 클라이언트에 서버용 비밀키를 요구하지 않는다.
- 이미지 2개 배치는 문서 구조에 저장하고 화면이 좁으면 한 열로 표시하는 안을 제안한다. 모바일에서도 배치 변경을 할 수 있게 한다.
- 드래그 외에 삽입 버튼·위/아래 이동·배치 메뉴·키보드 조작을 제공한다. 모바일 가상 키보드, 한글 조합 입력, 선택 영역, 복사·붙여넣기, 실행 취소·재실행을 검증한다.
- 글꼴은 서비스가 허용한 목록과 대체 글꼴을 사용하고 불필요한 전체 글꼴 다운로드를 피한다. 읽기 전용 뷰어는 편집 도구 없이 별도로 사용할 수 있게 한다.
- 본문 저장 API·자동 저장·DB 저장·브라우저 로컬 영속 저장·서버 문서 이력은 에디터가 수행하지 않는다. 편집 중 메모리 상태와 실행 취소 이력은 제공한다. 호스트가 문서 입출력과 변경 이벤트를 사용해 저장·불러오기·저장 실패 처리를 구현하도록 안내한다.
- 파일 업로드는 선택한 업로드 연결을 통해 수행하며 본문 저장과 구분한다. 기본 연결은 플랫폼 파일 서비스를 쓰되 외부 파일 서비스로 교체 가능하다. 파일 보존 정책은 호스트가 업로드 옵션으로 지정한다.
- 표·목록·체크리스트·인용·코드블록·링크·정렬·서식 제거를 편의 기능 후보로 제안한다. 실시간 공동 편집·댓글·문서 이력·AI 작성은 아직 요구하지 않았다.

**Markdown 붙여넣기 상세·검수 기준:**

- CommonMark와 GFM의 일반적인 문법을 지원 기준으로 제안한다. 제목, 문단, 굵게·기울임·취소선, 링크·이미지, 인용, 구분선, 순서/비순서·중첩 목록, 체크리스트, 인라인 코드·코드블록, 표를 블록·서식으로 변환한다. 위 문법에 필요한 블록은 첫 출시 범위에 포함한다.
- 코드블록의 줄바꿈·들여쓰기·언어 정보와 목록 중첩 구조를 보존한다. 한글·이모지·이스케이프된 문자가 손상되지 않아야 한다.
- 변환된 내용을 문서 데이터로 내보내 호스트 서비스가 저장하고 다시 입력했을 때 에디터와 읽기 전용 뷰어의 구조·서식이 일치해야 한다.
- 붙여넣기를 한 번의 실행 취소·재실행 단위로 처리하고, 코드블록 안에 붙여넣을 때는 코드를 다시 Markdown으로 해석하지 않는 동작을 제안한다. 원문 그대로 붙여넣는 방법도 제공한다.
- 클립보드의 HTML/일반 텍스트/Markdown 형식 처리 우선순위와 혼합 문서 변환 규칙을 명시한다. HTML·링크·이미지 입력을 검증해 임의 스크립트가 실행되지 않도록 한다.
- 수식·Mermaid·사용자 정의 HTML 등 확장 문법의 전용 렌더링은 별도 범위로 둔다. 미지원 문법은 내용을 조용히 버리지 않고 원문을 보존하는 대체 동작을 제공한다.
- 외부 이미지·상대 경로는 원문 링크를 보존하고 해석할 수 없는 경로·불러오기 실패를 표시한다. 붙여넣은 문서에 상대 경로만 있을 때 원본 PC의 파일을 자동으로 얻을 수 있다고 가정하지 않는다.
- 이 요구는 문서 내용 붙여넣기에 적용한다. `.md` 파일을 파일 첨부로 업로드하는 동작과 구분하고, 파일 가져오기 기능을 추가할 경우 별도로 명시한다.

**확정한 배포 방식과 상세 설계:**

- React·Vue에는 버전이 있는 npm 패키지와 연결 컴포넌트를 제공한다. 공통 코어·뷰어·스타일을 공유하고 각 서비스가 원하는 버전을 고정해 설치한다.
- 일반 HTML/JavaScript·JSP에는 빌드된 JS·CSS와 초기화 API를 제공한다. 서버 언어와 무관하게 브라우저에서 사용하며, 호스트가 자신의 정적 자산으로 복사해 제공할 수도 있다.
- npm 패키지는 패키지 레지스트리 또는 버전 고정 tarball로 배포할 수 있다. 공개 배포 여부·개인용 레지스트리·패키지 이름은 미정이다. Docker 레지스트리와 패키지 배포 방식을 구분한다. [npm 패키지 문서](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/)
- 플랫폼의 정적 파일 제공 경로를 이용할 경우 버전별 JS·CSS URL을 제공하고 기존 버전 파일을 덮어쓰지 않는다. 플랫폼 Docker 이미지는 이런 자산을 제공하는 역할을 할 수 있다.
- 에디터·뷰어 버전과 문서 JSON 버전의 호환 범위·변경 내역·업그레이드 예제를 제공한다. 중앙 배포가 기존 프로젝트의 설치 버전을 자동 변경하지 않게 한다.
- React·Vue·JSP/일반 JS별로 초기화, 값 입력·변경 이벤트, 호스트 저장, 뷰어 렌더링, 플랫폼/자체 업로드 연결, 자원 해제까지 실행 가능한 예제를 제공한다.

### 개발 환경 모의 연동 — F-12

**확정 요구:** 환경변수가 개발 모드이면 실제 카카오 로그인·이메일 등 외부 서비스를 사용하지 않고 가짜 인증과 연동 결과로 개발할 수 있어야 한다.

**설계 제안:**

- 서버가 해석하는 개발 환경 설정으로 소셜 로그인 3종과 외부 발송을 모의 제공자로 전환한다. 브라우저 URL·요청 파라미터만으로 모드를 전환하지 않는다.
- 개발 로그인 화면에서 테스트 사용자·프로젝트·실패 시나리오를 선택한다. 개발용 인증도 프로젝트별 사용자·권한 검사와 만료·콜백 검증 흐름을 거친다.
- 개발용 토큰의 발급자·키·저장 데이터를 운영과 분리한다. 운영 배포 구성에는 개발용 우회 경로를 노출하지 않으며 위험한 설정 조합은 시작 시 거부한다.
- 이메일·SMS·카카오·Telegram 등의 실제 발송은 모의 모드에서 발생하지 않는다. 개발 수신함에 내용과 가상 결과를 표시하고 성공·실패·지연·재시도를 재현한다.
- 앱 내 알림·에디터·개발용 파일 저장은 로컬 개발 데이터로 실제 동작시켜 검증한다. 웹 푸시는 모의 발송과 실제 브라우저 권한·구독 동작의 검증 범위를 구분한다.
- 개발 화면에 모의 모드임을 명확하게 표시하고 데이터를 초기화할 수 있게 한다. 실제 외부 연동을 검증할 별도 테스트 구성을 제공하며, 모의 성공을 운영 연동 검증 통과로 보고하지 않는다.

### 알림 채널별 범위

6개 채널의 포함과 이메일·SMS 제공 업체인 **네이버 클라우드 플랫폼(NCP)**은 확정이다. 아래 상세 동작은 제안이며 카카오 메시지 종류·제공 업체는 아직 미정이다.

| ID | 채널 | 제안하는 기본 동작 | 남은 결정 |
|---|---|---|---|
| F-05-01 | 이메일 | NCP를 통한 수신 주소·템플릿·변수 발송, 처리 이력 | 사용할 계정·프로젝트/API, 발신 주소, 첨부 지원 |
| F-05-02 | 앱 내 알림 | 프로젝트별 사용자 알림함, 목록·미읽음 수, 읽음 처리, 이동 링크 | 실시간 반영 방식, 보존 기간, 연동 예제 UI 범위 |
| F-05-03 | 웹 푸시 | 사용자 동의에 따른 브라우저 구독 등록·해제, 발송, 만료 구독 정리 | 지원 브라우저·기기, 구독 연결·해제 정책 |
| F-05-04 | SMS | NCP SENS를 통한 수신 번호·내용 발송, 처리 이력 | 사용할 계정·프로젝트, 발신 번호, 장문·이미지 메시지 포함 여부 |
| F-05-05 | 카카오 | 선정한 카카오 메시지 상품·API에 따른 발송과 상태 관리 | 메시지 종류, 제공 업체, 발신 채널과 템플릿 운영 방식 |
| F-05-06 | Telegram | 봇을 통한 등록된 대화 대상으로 발송, 처리 이력 | 봇 소유·프로젝트별 공유 여부, 개인·그룹 등 지원 대상 |

NCP의 SENS·Cloud Outbound Mailer 통합 안내를 기준으로 사용 중인 계정과 이메일 API를 확인한다. 기존 API 지원과 신규 서비스 설정을 구분해 연동하며 기존 서비스의 설정을 변경하지 않는다. [NCP 서비스 통합 안내](https://guide.ncloud-docs.com/docs/sens-integrationguide), [SENS API](https://api.ncloud-docs.com/docs/sens-overview).

공통 동작은 다음과 같이 제안한다.

- 요청에서 사용할 채널을 명시한다. 6개 지원이 모든 요청을 6개 채널로 일괄 발송한다는 뜻은 아니다.
- 하나의 요청에 여러 채널·수신자가 있으면 각 전달 건의 상태·재시도·중복 방지를 구분한다. 한 채널 실패가 다른 채널의 성공을 취소하거나 재발송하게 하지 않는다.
- 관리자 화면에서 프로젝트·환경·채널별 연결 설정, 템플릿, 시험 발송, 실패 이유를 확인한다. 설정되지 않은 채널은 사용 불가 상태와 이유를 표시한다.
- 최종 사용자의 수신 주소·번호·구독·Telegram 대화 대상은 프로젝트별 사용자와 안전하게 연결하고, 임의의 다른 사용자 대상으로 변경하는 것을 막는다.
- 앱 내 알림 조회·읽음 처리는 본인 알림으로 제한한다. 웹 푸시는 권한 거부·구독 해제·만료를 정상적인 상태로 처리한다.
- 수신 설정과 발송 제한 정책을 정한다. 채널 간 자동 대체 발송은 별도 합의 없이 수행하지 않는다.

### 이벤트 웹훅 — F-13

**확정 요구:** 파일 미리보기 생성 완료·실패, 알림 상태 변경 등을 연결된 서비스에 전달하는 웹훅을 첫 출시부터 제공한다.

**상세 제안:** 프로젝트·환경별 수신 URL·이벤트 종류·서명 키를 관리하고 시험 전송·전달 이력을 제공한다. 이벤트 ID·생성 시각·버전과 최소 필요한 데이터를 전송한다. 서명 검증·중복 처리 방지·재시도·실패 재전송 방법을 문서화한다. 수신 서비스는 동일 이벤트를 여러 번 받아도 안전하게 처리해야 하며 도착 순서를 보장한다고 가정하지 않는다. 수신 URL 검증·발송 제한과 내부 자원에 대한 임의 요청 방지 정책을 적용한다.

### 추가 후보 — 채택 전 구현 범위에 포함하지 않음

- 예약 알림, 확정한 6개 이외의 발송 채널, 고급 수신 규칙.
- 프로젝트별 관리자 위임, 사용량 추이, 공통 설정·기능 토글.
- 언어별 SDK: 실제 반복되는 연동 코드가 확인되면 도입.

## 4. 사용자 흐름

아래는 **제안**이며 프로젝트별 계정 분리와 알림 6개 채널을 전제로 가입 방식·채널별 연동 결정에 따라 구체화한다.

### A. 플랫폼 최초 운영

관리자가 이미지 태그와 환경변수 설정 → Compose로 실행 → 안전한 최초 관리자 설정 → 로그인 → 저장소·발송 채널 연결 확인 → 첫 프로젝트 생성.

고정된 기본 관리자 비밀번호를 제공하지 않는다. 초기 설정을 완료한 뒤에는 초기 관리자 생성 경로를 제한한다.

### B. 신규 프로젝트 연동 — F-01, F-02, F-03, F-09

관리자 화면에서 프로젝트 생성 → 개발 환경 등록 → 인증 콜백·허용 출처·필요 기능 설정 → 자격증명 발급 → 연동 안내에 따라 프로젝트 설정 → 예제로 로그인·파일·알림 확인 → 운영 환경을 별도로 등록.

운영용 자격증명과 데이터는 개발 환경에서 공유하지 않는다. 플랫폼 자격증명 변경이 필요한 경우 교체 절차를 안내한다.

### C. 최종 이용자 로그인 — F-02

연결된 서비스에서 로그인 선택 → 플랫폼 인증 화면 → 가입 또는 인증 → 서비스로 복귀 → 서비스에서 사용자 신원과 이용 권한 확인 → 기능 사용.

로그인 취소, 잘못된 콜백, 만료된 요청, 정지 계정, 권한 없는 프로젝트 접근 시 안내와 복귀 경로를 제공한다. 프로젝트 A의 플랫폼 세션으로 프로젝트 B에 로그인시키지 않는다. B는 별도 인증 흐름을 거치되 소셜 제공자의 기존 세션에 따라 비밀번호 재입력 여부는 달라질 수 있다. 한 프로젝트의 로그아웃·정지·비밀번호 변경으로 다른 프로젝트의 플랫폼 계정을 변경하지 않는다.

### D. 파일 이용 — F-04

서비스에서 파일 선택 → 사용자·프로젝트 권한과 제한 확인 → 업로드 → 완료된 파일 정보 저장 → 권한 있는 사용자 조회·다운로드 → 정책에 따른 삭제.

중단·실패 업로드는 완료 파일로 노출하지 않는다. 실제 파일과 메타데이터 중 일부만 남은 경우를 정리하는 정책을 둔다. 업로드 재시도와 만료 링크 재발급을 지원할 범위를 확정한다.

### E. 알림 처리 — F-05

서비스에서 사용할 채널과 수신 대상을 지정해 알림 요청 → 권한·수신 대상·템플릿 검사 → 요청을 영속 저장하고 접수 식별자 반환 → 채널·수신자별 전달 작업 → 처리 결과 저장 → 서비스 또는 관리자가 조회.

앱 내 알림은 대상 프로젝트 사용자의 알림함에 저장하고 조회·읽음 흐름으로 이어진다. 웹 푸시는 사전 구독 등록과 사용자 연결을 거친다. 외부 채널은 선정한 제공자의 연동 계약에 따른다.

일시 오류는 제한된 횟수로 재시도하고 영구 오류는 실패 사유를 남긴다. 같은 요청의 재접수는 중복 처리 방지 키로 제어한다. 외부 채널의 응답 유실 시 중복 전달 가능성과 처리 정책을 명시한다.

### F. 관리자 장애 대응 — F-06, F-07, F-08

오류·실패 상태 발견 → 프로젝트·환경·기간으로 필터 → 요청 식별자로 관련 이력 확인 → 원인 조치 → 허용된 작업 재시도 → 결과와 조치 이력 확인.

### G. 문서 편집·읽기 — F-04, F-11

서비스에서 에디터 로딩 → 블록·서식 입력 → 슬래시 명령/붙여넣기/드래그로 파일 삽입 → 업로드 상태 확인 → 이미지 배치 → 서비스의 저장 동작 → 같은 문서를 뷰어로 열어 결과 확인.

에디터는 업로드 실패·만료된 파일 URL·권한 없음·삭제된 첨부를 구분해 표시한다. 본문 저장 완료·실패·동시 수정 충돌은 호스트 서비스가 처리한다. 작성 취소 후 남은 파일은 선택한 보존 정책 또는 서비스가 요청한 명시적 정리에 따른다.

### H. 외부 서비스 없는 개발 — F-12

개발 환경 설정으로 실행 → 개발 표시 확인 → 테스트 사용자로 인증 → 파일·에디터·알림 흐름 실행 → 개발 수신함과 실패 시나리오 확인 → 개발 데이터 초기화.

### 제안하는 공통 UX 기준

- 한국어를 기본으로 하며 데스크톱에서 운영 작업을 편하게 수행한다. 모바일에서는 최소한 상태 확인과 주요 상세 조회가 가능해야 한다.
- 현재 프로젝트와 환경을 항상 식별할 수 있게 한다. 운영 환경의 위험 작업은 대상과 영향을 확인한 후 실행한다.
- 목록은 검색·필터·페이지 이동을 제공한다. 데이터가 많아도 전체 항목을 한 번에 로딩하지 않는다.
- 로딩, 처음 사용하는 빈 화면, 검색 결과 없음, 오류, 권한 없음, 저장 완료 상태를 구분한다.
- 설정 오류는 해당 필드에 이유를 표시하고 입력 내용을 보존한다. 저장 실패를 성공처럼 표시하지 않는다.
- 자격증명 비밀값은 필요한 시점에만 노출하고 이후 마스킹한다. 로그·화면 주소·일반 설정 예시에 비밀값을 남기지 않는다.
- 상태는 색상과 텍스트를 함께 사용한다. 키보드 이동, 포커스 표시, 입력 레이블, 읽기 순서와 명도 대비를 검증한다.
- 관리자 화면 외에 최종 이용자가 만나는 로그인·가입·계정 복구 화면도 범위에 포함한다.
- 시각 스타일, UI 라이브러리, 정확한 지원 화면 크기와 브라우저는 미정이다.
- 파일 화면에는 미리보기 생성 상태·최근 이용·삭제 예정·보존 설정을 포함한다. 에디터·파일 뷰어는 독립 삽입과 스타일 조정을 지원한다.
- 관리자 모바일 조회 기준과 별도로 에디터는 모바일 편집까지 지원한다. 좁은 화면에서 열 배치를 바꾸되 저장한 문서의 원래 배치 정보는 보존한다.

### 제안하는 주요 데이터

| 영역 | 데이터 |
|---|---|

| 인증 | 사용자, 인증 수단, 프로젝트 이용 관계·역할, 인증 클라이언트, 세션 |

| 파일 | 파일 식별자, 저장 위치, 원래 이름, 형식·크기, 프로젝트·소유 관계, 접근·변환 상태, 파생 파일, 공유 설정, 최근 이용·보존·삭제 상태 |
| 알림 | 채널 설정, 템플릿, 프로젝트별 수신 대상·수신 설정·웹 푸시 구독, 앱 내 알림·읽음 상태, 요청·중복 방지 키, 채널/수신자별 발송 시도·결과 |

| 파일 보존 정책 | 코드, 고정/사용자 등록 구분, 표시 이름, 현재 기간 값·단위 또는 영구 여부, 사용 상태, 변경 이력; 파일은 코드를 참조 |
| 파일 공유 | 공개 여부, 공유 링크·범위·만료·철회 상태, 비밀번호 검증 정보 |
| 웹훅 | 프로젝트·환경별 수신 설정, 이벤트, 전달 시도·결과, 서명 키 관리 정보 |
| 업로드 세션 | 프로젝트·환경·소유자, 예상 크기·파일 확인 정보, 수신 위치/조각, 진행·완료 상태, 만료 시각, 완료 파일 연결 |
| 에디터 연동 데이터 | 버전이 있는 문서 JSON, 블록·서식·이미지 배치·파일 참조 정보; 호스트 서비스 소유·저장, 플랫폼 DB 저장 대상 아님 |
| 개발 모드 | 운영과 분리된 테스트 사용자, 모의 발송 결과·수신함, 오류 시나리오 |

계정 데이터는 프로젝트별로 분리한다. 프로젝트 소유 데이터는 프로젝트·환경 경계를 명확히 하고, 보호된 조회와 관리 작업에서 인증된 주체의 권한을 검증한다. 공개 파일은 정의된 URL 조회에 한해 익명 접근을 허용한다. 요청 본문의 프로젝트 ID만 신뢰하지 않는다. 사용자를 이메일 하나로 전역 식별하지 않으며, 인증 발급자와 사용자 식별자의 조합 등으로 소속을 구분한다. 다른 프로젝트에서 발급된 토큰은 보호된 API의 접근 권한으로 인정하지 않는다.

### 제안하는 연동 계약

- 로그인 연동은 OpenID Connect를 기본 후보로 한다. 이는 OAuth 2.0 위에 사용자 신원 확인을 정의한 표준이다. [OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0.html)
- 인증 흐름은 Authorization Code와 PKCE를 기준으로 설계하고, 클라이언트 유형에 따른 토큰 저장·검증·갱신·폐기 정책을 정한다. [OAuth 보안 권고 RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html)
- 파일·알림·관리 API는 버전, 요청·응답 형식, 오류 코드, 페이지 조회 규칙을 문서화한다. 표준 인증 엔드포인트와 일반 업무 API의 버전 규칙은 구분한다.
- API에는 인증 방식, 필요한 권한, 제한, 재시도 가능 여부와 예제를 포함한다.
- 재시도할 수 있는 생성·발송 작업에는 중복 방지 정책과 적용 범위를 정한다.
- 외부 저장소·발송 제공자의 지연이나 오류를 기록하고, 사용자가 복구 가능한 상태로 표현한다.
- 사용자 데이터, 알림 본문, 파일, 로그의 보존·삭제·백업 보존 기간을 각각 결정한다.
- 계정 삭제는 해당 프로젝트의 파일·발송 이력에 대한 정책에 따라 처리하고 다른 프로젝트의 별도 계정을 삭제하지 않는다.

### 확정된 연동 경계

기존 API 호환과 기존 데이터 이전은 요구하지 않는다. 기존 서비스·데이터는 유지한다. 사용자가 제안한 기존 외부 소셜 앱의 새 콜백 추가는 적용 가능성을 검토하되 기존 키·콜백을 유지하는 조건이며, 아직 실제 설정을 변경하지 않았다.

### 미정

- 파일 저장소 종류·위치, NCP 계정·발신 설정, 카카오 발송 제공자와 메시지 종류, Telegram 봇 설정, 사용할 도메인과 TLS 종료 위치.
- 기존 세 저장소의 기능 목록과 새 플랫폼에서 유지·개선·제외할 항목. 내부 검토 후 별도 추측 없이 반영한다.

## 7. 기술 스택

### 확정

- 개발과 운영은 Docker 기반으로 구성한다.
- 운영 배포는 빌드된 이미지와 Compose 설정을 사용한다.
- 백엔드 빌드 도구는 Gradle을 사용한다. 빌드는 Docker 내부에서 실행한다.
- 인증 엔진은 Keycloak을 사용한다. 자체 인증 서버를 별도로 개발하는 안은 채택하지 않는다.
- 내부 서비스는 MSA 방식으로 개발·배포한다.
- 에디터는 React·Vue용 패키지와 JSP·일반 HTML/JavaScript용 버전별 JS·CSS로 제공한다.

### 선택 원칙 — 제안

- 합의한 MSA 경계 안에서 한 명이 개발·운영하기 쉬운 구성을 우선한다. 기능별 서비스는 독립적으로 빌드·배포할 수 있게 하고 서비스 경계를 넘는 직접 DB 접근을 피한다.
- 사용자에게 익숙한 백엔드 언어·프레임워크를 우선 검토한다.
- 인증 프로토콜·암호화는 Keycloak과 검증된 구성요소를 활용한다. 신규 코드에서는 프로젝트 관리와 서비스별 권한·연동을 구현한다.
- 영속 작업·재시도가 필요한 알림은 API 응답 시간과 외부 발송 시간을 분리한다. DB 작업 테이블 또는 별도 큐 선택은 예상 처리량과 운영 부담을 보고 결정한다.
- 프론트엔드, 백엔드, DB, 파일 저장소, 인증 구성요소, 작업 처리 방식, 프록시, CI/이미지 빌드 방식을 확정 목록으로 관리한다.
- 버전은 구현 착수 때 지원 상태·이미지 아키텍처·호환성을 확인한 뒤 고정한다.

### 기술 구성 — 확정 사항과 후보

Keycloak·MSA·Docker Compose·Gradle·에디터 배포 방식은 확정이다. 첫 실행 기반에는 Java 21·Spring Boot 4.1.1·Gradle 9.7.1·PostgreSQL 17.11을 적용했다. 실제 이미지와 서비스 경계는 [실행 기반 문서](ARCHITECTURE.md)를 따른다. 프론트엔드·에디터 등 아직 구현하지 않은 영역은 아래 후보를 검토한다.

| 영역 | 추천 | 선택 이유·조건 |
|---|---|---|
| 관리자 웹 | React + TypeScript + Vite | 관리 기능 중심의 웹 앱 구성; 서버 렌더링 요구는 현재 없음 |
| 에디터·뷰어 | 공통 TypeScript 코어·UI + React·Vue·일반 JS 연결 | Tiptap/ProseMirror 우선 검토; 독립 배포와 문서 형식 호환 필요 |
| 서비스별 API | Java + Spring Boot + Gradle — 적용 | 프로젝트 관리·파일·알림을 독립 서비스로 구성 |
| 인증 엔진 | Keycloak — 확정 | 프로젝트별 인증 영역과 표준 로그인·계정 관리 |
| DB | PostgreSQL — 적용 | 하나의 DB 서버에 서비스별 DB·접속 계정을 분리 |
| 파일 저장 | 초기에는 Docker 영속 볼륨 | 단일 운영 서버 전제의 간단한 구성; 다중 서버·대규모 파일이면 오브젝트 스토리지 재검토 |
| 알림 작업 | DB에 저장한 작업을 백그라운드 처리 | 접수 데이터와 재시도 상태를 영속화; 초기에는 별도 메시지 브로커 없이 시작 |
| 로그 | 구조화된 컨테이너 로그 + DB 감사 기록 | 회전·용량 제한과 조회 범위를 정하고 플랫폼 진단에 집중 |
| 배포 | Docker Compose + 자체 레지스트리 | 사용자가 지정한 배포 방식 적용 |

추천 조합은 개발·초기 운영 후보이며 특정 CPU 모델이나 고정 메모리 예산을 전제로 하지 않는다. 실제 수용 가능한 트래픽은 배포 환경별 부하 검증으로 확인한다. UI 컴포넌트 라이브러리, 프록시, 정확한 버전과 이미지 구성은 후속 설계에서 정한다.

플랫폼 구성요소의 CPU·메모리 설정은 배포 환경에 맞춰 Compose·환경변수로 조정할 수 있게 한다. 소스 수정이나 이미지 재빌드 없이 설정을 적용하는 절차를 제공한다. 실행 중인 서비스에 설정을 반영할 때 필요한 재시작·컨테이너 재생성 여부도 문서화한다. JVM 등 내부 메모리 설정은 컨테이너 자원 설정과 함께 검증한다.

기술 확인 자료: [Spring Boot 공식 문서](https://docs.spring.io/spring-boot/reference/index.html), [Vite 시작 안내](https://vite.dev/guide/), [PostgreSQL 공식 문서](https://www.postgresql.org/docs/current/index.html).

### 확정한 Keycloak 사용 범위

- Keycloak의 realm은 사용자·자격증명·역할 등을 관리하는 분리된 인증 영역이다. 프로젝트별 realm 구성을 추천하고, 환경별 분리도 추가 제안한다. [Keycloak realm 설명](https://www.keycloak.org/docs/latest/server_admin/index.html#core-concepts-and-terms)
- 통합 관리자 화면, 프로젝트 관리, 파일·알림 서비스, 연동 안내는 새 코드로 개발한다. 인증 처리의 기반은 Keycloak을 사용한다.
- 관리자 화면에서 필요한 사용자·인증 설정 작업을 플랫폼 API를 통해 제공한다. 브라우저에 Keycloak 관리용 비밀 자격증명을 노출하지 않는다.
- 애플리케이션 간 사용자 공유·계정 연결·공통 외부 IdP 연동으로 프로젝트 분리가 약화되지 않도록 설정과 실제 로그인 흐름을 검증한다.
- Keycloak 원본 DB에 직접 쓰지 않고 공식 관리 API를 이용한다. 사용자·인증 상태의 원본과 플랫폼 데이터의 책임을 분리한다.
- realm 격리는 계정의 논리적 분리다. 서버·DB 장애까지 프로젝트별로 분리하는 물리적 격리는 별도 요구이며 현재 확정하지 않았다.
- 기존 서비스 코드는 사용하지 않고 인증 기반은 Keycloak을 활용한다. Keycloak 버전·확장·테마와 서비스 연동을 관리한다.

### MSA 구성안

| 구성요소 | 책임 | 배포 단위 |
|---|---|---|
| Nginx | 외부 진입·경로 라우팅·정적 자산 전달 | 프록시 컨테이너 |
| 프로젝트 관리 서비스 | 프로젝트·환경·설정·관리 권한·통합 운영 API | 독립 서비스 이미지 |
| 인증 서비스 | Keycloak, 프로젝트별 인증 영역·세션·로그인 | 독립 컨테이너 |
| 파일 서비스 | 업로드 세션·원본·미리보기·공유·보존 정책 | 독립 서비스 이미지; 변환 작업 실행 방식은 설계 |
| 알림 서비스 | 6개 채널·템플릿·발송 작업·이력·웹훅 전달 | 독립 서비스 이미지; 작업 실행 방식은 설계 |
| 관리자 웹 | 통합 운영 UI·연동 안내·개발 도구 | 독립 빌드 자산/이미지 |
| 에디터·뷰어 | 호스트에 설치하는 공통 패키지·정적 자산 | 버전별 패키지와 JS·CSS; 문서 저장 서버 없음 |

서비스 간에는 Docker 내부 네트워크의 서비스 이름으로 통신한다. 필요한 동기 API·이벤트 계약·인증 방식을 문서화한다. 각 서비스는 자신의 데이터와 DB 변경을 소유하며 다른 서비스 DB에 직접 쓰지 않는다. 서비스 간 작업의 부분 실패는 재시도·중복 방지·상태 조회로 복구하도록 설계한다. MSA를 이유로 메시지 브로커나 서비스 메시를 자동으로 추가하지 않는다.

## 9. 제약사항

### 확정

- 개발과 운영은 Docker를 기본으로 한다.
- 운영 서버에는 원칙적으로 `compose.yml`과 환경변수 파일을 배포하고 이미지를 받아 실행한다.
- 자체 이미지 이름은 `register.shnea.kr/platform-이미지명:태그` 형식을 따른다.
- macOS와 Windows를 번갈아 사용해 개발할 수 있어야 한다.
- 운영 서버는 Linux다.
- CPU·메모리 자원 설정은 배포 환경에 맞게 조정 가능해야 하며, 특정 CPU 모델·메모리 용량을 고정 요구사항으로 두지 않는다.
- 기본 외부 진입 포트는 Nginx의 `30140`이다. 추가 외부 포트는 `30141`부터 1씩 증가시키며 DB 외부 노출 포트는 `30141`로 배정한다.
- Git 저장소는 `https://git.shnea.kr/shnea/platform.git`이다. 완료한 작업 단위마다 필요한 검증 후 한글 커밋 메시지로 커밋·푸시한다.
- 작업 중단·개발 PC 변경 후 이어갈 수 있도록 현재 단계·완료/미완료·검증 결과·다음 작업을 `docs/STATUS.md`에 기록한다. 프로젝트 작업 규칙은 루트 `AGENTS.md`에 둔다.

### 포트 배정 규칙

| 외부 포트 | 용도 |
|---|---|
| `30140` | Nginx 기본 진입점 |
| `30141` | DB 접근이 필요한 경우 사용 |
| `30142` 이후 | 추가 외부 노출 서비스에 순차 배정하고 이 표에 기록 |

이 규칙은 호스트에 공개하는 포트에 적용한다. 컨테이너 내부 포트는 각 서비스 설정을 사용하며, 내부 통신만 필요한 서비스에는 외부 포트를 배정할 필요가 없다. MSA API는 기본적으로 Nginx를 통해 접근한다. 포트의 기본 배정은 유지하되 실제 바인딩 주소·환경별 충돌 조정은 Compose·환경변수로 관리한다.

### 제약의 적용 방식 — 제안

- 운영 서버에서 소스를 빌드하지 않는다. 실행에 필요한 정적 설정은 이미지에 포함하거나 환경변수에서 안전하게 생성한다.
- 이미지와 환경변수 파일에 사용자 데이터·업로드 파일을 저장하지 않는다. DB와 파일의 영속 볼륨 또는 외부 저장소, 백업 공간을 별도로 확보한다.
- `.env`는 비밀정보를 포함할 수 있으므로 저장소에 커밋하지 않고 접근을 제한한다. 비밀값 없는 예시 파일을 제공한다.
- 설치·인프라 설정은 환경변수로, 관리자 화면에서 바꾸는 프로젝트 정책·일반 운영 설정은 DB로 관리하는 방안을 제안한다. 외부 발송 비밀키 등은 저장·암호화·교체 방식을 별도로 정의한다.
- 호스트의 개인 절대 경로, 특정 셸, OS 전용 스크립트에 의존하지 않는다. 줄바꿈·파일명 대소문자·볼륨 권한·파일 감시 차이를 검증한다.
- macOS/Windows 개발에서도 Linux 컨테이너 사용을 제안한다. 실제 CPU가 다르면 `linux/amd64`·`linux/arm64` 지원 또는 에뮬레이션 방식을 정한다. Docker 이미지는 대상 OS/CPU와의 호환이 필요하다. [Docker 다중 플랫폼 빌드 문서](https://docs.docker.com/build/building/multi-platform/)
- 자체 이미지 태그는 배포 버전을 식별할 수 있게 고정한다. DB 변경이 있는 버전은 이미지 태그 복원만으로 되돌릴 수 있는지 검토하고 별도 복구 절차를 제공한다.

### 미정

- 배포 시 사용할 자원 설정과 검증 환경, 디스크·파일 저장 위치, 기존 프록시·TLS·외부 DB·스토리지 유무.
- 일정과 운영비 상한. 기존 서비스 이전은 범위 밖이다.
- 외부 기반 이미지도 자체 레지스트리로 복제해야 하는지.

## 10. 하지 않을 것

다음 항목은 **확정된 제외 범위**다.

- 기존 세 서비스 코드의 복사·재사용은 사용자 요구에 따라 제외한다.
- 기존 서비스·연결 프로젝트의 이전, 교체, 중단, 데이터 변경 및 기존 API의 완전 호환은 사용자 결정에 따라 제외한다.
- 프로젝트 사이의 통합 계정·SSO와 동일 이메일 계정의 자동 연결은 사용자 결정에 따라 제외한다.
- 에디터·플랫폼의 문서 본문 저장 기능과 자동 저장은 제외한다. 저장 주체는 각 연결 서비스다.

아래는 아직 채택하지 않은 **1차 제외 후보**다. 제외 결정은 후속 개발의 영구 금지를 의미하지 않는다.

- 외부 고객에게 플랫폼을 판매하는 가입·과금·조직별 셀프서비스 기능.
- 연결된 서비스의 게시판·주문 등 개별 사업 기능.
- 모든 언어용 SDK와 확정한 6개 이외의 알림 채널 제공. 확정한 6개 채널은 이 제외 후보에 해당하지 않는다.
- 모든 서비스의 로그를 수집하는 범용 분석 제품, Kubernetes·다중 지역 고가용성 구축.
- 필요가 확인되지 않은 플러그인 시스템, 범용 워크플로 엔진, 기능 토글 플랫폼.
- 모든 파일 형식의 완벽한 미리보기·영상 변환, 실시간 공동 편집·문서 댓글·AI 작성. 사용자가 요구한 폭넓은 업로드와 기본 에디터 기능은 포함한다.

### 현재 남은 결정

1. Keycloak·MSA는 확정. 언어·프레임워크·DB의 지원 버전, 서비스 경계·계약·인증 확장 방법을 구체화한다.
