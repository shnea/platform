# 작업 상태와 다음 작업

## 현재 단계

### NAS Loki 설정 파일 읽기 권한 오류 수정 (2026-09-27)

- 사용자가 운영 파일 업로드 후 유형/날짜 폴더와 `original.png`·`thumbnail.jpg` 생성을 확인했다. 이어 로그 메뉴의 `LOG_BACKEND_UNAVAILABLE`(요청 ID `17b27bcb13b4c1d0b05a6ba8bb480cc4`)을 보고했다. NAS 출력에서 Loki `Restarting (1)`과 `open /etc/loki/platform.yml: permission denied`를 확인했다.
- 기존 배포 ZIP의 Loki 설정 파일 권한은 `600`(create_system=0)이었다. ZIP 생성기가 일반 설정에 명시적 권한을 주지 않는 문제를 수정해 일반 파일은 Unix 일반 파일 `644`, 실제 `.env.prod`는 기존 `600`으로 보존한다. NAS 배포 명령에도 해당 비밀값 없는 설정 파일 하나에 대한 `chmod 644`를 포함했다. Docker 컨테이너를 root로 변경하거나 데이터 전체 권한을 열지 않는다.
- **검증:** `python scripts/package-nas.py` 및 `python scripts/package-nas.py --env-file .env.prod`로 두 ZIP을 갱신했다. ZipFile로 각 파일 목록·Unix 일반 파일 속성·설정 644/비밀값 600·UTF-8을 확인했다. 실제 비밀값은 출력/커밋하지 않았다. 이미지 변경이나 재빌드는 필요 없다.
- **운영 확인:** 사용자가 NAS에서 설정 파일 `chmod 644`와 Loki 재시작을 실행했다. 회신 로그의 `Loki started`, WAL 복구 오류 없음, scheduler 요청 수락을 통해 기동 복구를 확인했고, 이후 관리자 로그 화면에서도 오류가 사라졌다고 확인했다. 이번 설정 파일 권한 장애는 해결 완료다. 외부 프로젝트의 신규 로그 수집 전체 흐름과 백업·복원 검수는 별도로 남는다. 상주 프로세스 추가 없음.

### 파일 유형·날짜별 실제 저장 폴더 정리 (2026-09-27)

- 새 업로드는 `/app/storage/유형/YYYY/MM/DD/프로젝트ID/환경ID/파일ID/`에 원본(`original.확장자`)·썸네일(`thumbnail.jpg`)·영상 스트리밍(`hls/변환ID/`)을 함께 저장한다. NAS 루트는 기존 `/volume2/homes/platform/files`다. 유형은 이미지·영상·오디오·문서·압축·기타이며 확장자 분류와 실제 콘텐츠 검증은 구분한다. 원래 이름은 DB와 다운로드 응답에 유지한다.
- 한국 시간 업로드 접수일의 상대 경로를 V9 `files.storage_path`에 저장한다. 재개·재시작에도 경로가 유지된다. V9 이전 행은 NULL로 남겨 기존 평면 UUID 파일·썸네일·HLS와 진행 중 업로드를 그대로 사용하며 자동 이동하지 않는다. 접근 권한·URL·보존 정책 계약은 유지한다.
- `code-review` 기준으로 원본 이름의 경로 미사용, 저장 루트 밖 경로 거부, 파일별 정리 범위, DB 롤백 후 재개와 기존 경로 호환을 검토했다. 기존 데이터의 대량 이동이나 새 의존성은 없다.
- **검증:** `docker compose -p platform-job-checks -f compose.jobs-test.yml up --abort-on-container-exit --exit-code-from check` 통과. 프로젝트 57·알림 19·파일 60개, 총 136개 모두 통과(실패·건너뜀 0). 한국 자정 경계·유형/확장자·빈 파일·재시작·기존 업로드 재개·썸네일/HLS 경로·이웃 파일을 보존하는 삭제·경로 이탈 거부를 포함한다. `docker compose --env-file .env.build build file-service`로 배포 이미지 빌드 통과. 실제 NAS 미디어 생성·재생 재검수는 수행하지 않았다.
- **운영 상태/다음 작업:** 사용자가 앞선 NAS 기동 성공을 확인했다. 이번 파일 서비스 이미지는 로컬 빌드까지만 완료했고 레지스트리 게시·NAS 재배포는 수행하지 않았다. 사용자가 기존 `.env.build`의 push, NAS `.env.prod`의 pull/up 명령으로 반영하면 V9가 적용된다. 이후 새 파일 업로드·썸네일·영상 재생과 volume2 폴더 확인이 다음 운영 검수다. 격리 테스트 컨테이너는 종료·정리하며 상주 프로세스는 추가하지 않는다.

### NAS CPU CFS 제한 미지원 대응 (2026-09-27)

- 사용자의 최신 `up -d`는 네트워크/구성 해석을 통과하고 컨테이너 생성에서 `NanoCPUs can not be set`으로 중단됐다. NAS 커널의 CFS CPU quota 미지원에 맞춰 실제 `.env.prod`의 `*_CPUS` 8개만 0으로 수정했다. 비밀값·메모리·개발 CPU 설정은 유지한다.
- 두 운영 환경 생성 경로(`init-env.py --nas`, `prepare-environments.py`)에도 같은 규칙을 반영했다. `check-nas-config.py`로 모든 NAS 서비스의 CPU 제한 없음·메모리 제한 유지를 검증하고 배포 ZIP을 갱신했다. NAS에서는 운영 파일 CPU 설정 수정 후 동일한 `up -d`를 재실행하면 되며 이미지 재빌드/다운로드는 필요 없다. 실제 NAS 기동 성공은 사용자 확인 전이다.

### NAS Docker 기본 주소 대역 소진 대응 (2026-09-27)

- 사용자는 이미지 다운로드 후 `up -d`에서 `could not find an available, non-overlapping IPv4 address pool`을 보고했다. 제공한 NAS 라우팅 표에서 172.17~31의 /16, 192.168.16~240의 /20 및 LAN 192.168.0.0/24가 사용 중이었다.
- NAS 구성에 앱 `10.250.10.0/24`, DB `10.250.11.0/24`, 로그 `10.250.12.0/24` IPAM을 지정했다. 제공된 라우팅 표 및 세 대역끼리 겹치지 않는다. 기본 구성의 DB·로그 내부 전용 속성, 기존 서비스·환경 파일·비밀값·데이터 경로는 유지한다.
- `python -X utf8 scripts/check-nas-config.py`로 Compose 병합·대역 비중복·내부망 격리를 검증하고 배포 ZIP을 다시 생성했다. NAS 자체 재실행은 사용자 검수이며 아직 성공으로 표시하지 않는다. NAS의 `compose.nas.yml` 하나만 교체한 뒤 `sudo docker-compose --env-file .env.prod up -d` 재실행이 다음 단계다. 빌드·push·pull이나 기존 Docker 네트워크 삭제는 필요 없다.

### 배포 명령 간소화·환경 파일 3개와 NAS 배포 ZIP 준비 (2026-09-27)

- **최신 사용자 지시:** `.env.dev`·`.env.build`·`.env.prod` 이름을 고정하고 파일 이름 변경·수동 비밀값 입력 없이 복사 후 실행한다. 기존 `.env`의 내부 키·DB/관리자 비밀번호·NCP·소셜 설정을 개발·운영 파일에 그대로 반영했다. 개발 데이터 이전은 하지 않는다. 세 실제 파일과 비밀값 포함 ZIP은 Git 제외다. 기존 `.env`의 비밀번호는 변경하지 않았고 기본 Compose 파일 선택용 누락 설정만 추가했다.
- **구성:** 로컬 개발은 `docker compose --env-file .env.dev up -d --build`, 배포 이미지는 `docker compose --env-file .env.build build`·`push`, NAS는 `sudo docker-compose --env-file .env.prod pull`·`up -d`. 빌드 전용 `compose.build.yml`에는 자체 이미지 8개만 있고 런타임 비밀값·포트·볼륨은 없다. 사용자 수정 레지스트리 `registry.shnea.kr`를 보존하고 모든 Compose 이미지에 `IMAGE_REGISTRY`·`IMAGE_TAG`를 적용했다. 빌드/운영 파일 태그는 `0.1.0`으로 일치한다.
- **자동 준비:** NAS는 세 데이터 디렉터리를 기존 volume2 경로에 직접 bind한다. `storage-init`은 네트워크 없는 읽기 전용 루트 컨테이너에서 빈 디렉터리만 생성/소유권 설정하며 비어 있지 않은 기존 폴더는 변경하지 않는다. Keycloak healthy → identity-setup 성공 → project-service 순서로 시작한다. 초기화 컨테이너 `Exited (0)`은 정상이며 별도 setup 명령이 필요 없다.
- **검증:** `docker compose build`와 최종 `docker compose --env-file .env.build build` 각각 8개 빌드 통과. `python -X utf8 scripts/check-nas-config.py`로 환경 파일 선택·태그/레지스트리·빌드 전용 8개 서비스·운영 포트/마운트/시작 순서를 확인했다. 실제 tools 이미지의 tmpfs `/data`에서 `check-storage.py`로 소유권·권한·반복 실행 보존·심볼릭 링크 거부 통과. 격리 `platform-bootstrap-check`에서 빈 DB로 운영 인증 자동 초기화·MFA 설정·project-service healthy, 같은 up 명령 재실행 통과 후 컨테이너/볼륨 정리했다. DEV 스택이나 NAS는 재기동하지 않았다.
- **파일 검수:** 배포 문서를 PowerShell 파이프로 저장하며 한글이 `?`로 변한 오류를 발견해 UTF-8 원문으로 복구했다. 실제 파일과 ZIP 내부 문서의 한글·대체문자 부재를 확인했다. 개발/운영 비밀값·외부 연동 설정이 기존 `.env`와 일치하고 빌드 파일에 비밀값이 없음을 값 출력 없이 검사했다.
- **인계:** `output/releases/platform-nas-deploy.zip`에는 **`.env.prod` 원래 이름 그대로**와 Compose·Loki·안내 파일이 있다. `/volume1/docker/prod/platform`에 복사 후 안내된 두 NAS 명령을 실행한다. `python scripts/package-nas.py --env-file .env.prod`로 같은 형태를 다시 묶을 수 있다. 이 ZIP은 비밀값을 포함하므로 공개하지 않는다. 이미지 push·NAS 실행·DSM ACL·프록시 실IP·실제 백업/복원은 아직 수행하지 않았다. 이전 수동 생성/이름 변경/긴 `-f` 안내는 이 절과 최신 NAS 문서로 대체한다.

### 외부 Job·공통 로그·연결 지침과 NAS 배포 준비 완료 (2026-09-27)

- **최신 합의:** 외부 프로젝트의 워커가 작업을 가져가 실행한다. 플랫폼은 큐·상태·재시도·감사를 관리하며 외부 실행 코드를 받지 않는다. NAS 배포는 사용자가 직접 하며 개발 데이터·실제 `.env`를 이전하지 않는다. 배포 루트는 `/volume1/docker/prod/platform`, DB·파일·로그 데이터는 `/volume2/homes/platform/{postgres,files,loki}`다.
- **외부 Job:** 환경별 `jobs:write/read/work` 키로 등록·조회·점유·점유 연장·완료/실패·취소·재접수를 제공한다. UUID 접수 중복 방지, 60초 점유, 만료 워커 거부, 최대 10회 실행, 점유 만료 복구, 실행 이력·감사와 완료 후 30일 보존을 구현했다. 호스트 업무의 중복 방지는 호스트 책임이다. 내부 Job과 별도 테이블·관리자 탭이며 기존 키에 새 권한을 자동 부여하지 않는다.
- **공통 로그:** `logs:write/read`로 환경별 수집·검색·요청/Trace 추적을 제공한다. 프로젝트 서비스가 환경 UUID를 tenant로 정하고 외부 tenant 헤더는 사용하지 않는다. Loki 3.7.0은 전용 내부 네트워크·영속 볼륨을 사용하고 호스트 포트는 없다. 7일 보존, 환경별 하루 10 MiB·10,000회·분당 120회, 배치 100건/256 KiB, 마스킹·전송 제한·장애 응답을 적용했다. 자동 마스킹이 모든 개인정보를 검출하는 것은 아니며 송신 측 비밀값 제외가 필요하다.
- **화면·공개 자료:** 독립 로그 메뉴에 검색·조회 결과 분포 차트·상세·같은 요청 조회·한국어 오류/재시도를 추가했다. 개발자 센터의 `Job·로그 연결`에서 지침·OpenAPI·표준 라이브러리 Python 워커/비동기 로그 전송기를 받는다. [AI 연결 진입점](https://platform.shnea.kr/integrations/SERVICE_INTEGRATION.md)은 54줄, 무인증 공개 링크 15개다. 관리자/내부 계약은 공개 명세에서 제외한다.
- **DB·계약 검증:** `docker compose -p platform-job-checks -f compose.jobs-test.yml up --abort-on-container-exit --exit-code-from check`로 실제 PostgreSQL 격리 DB 테스트 **122개, 실패·오류·누락 0**. 동시 점유/중복 접수, 만료·재시도·취소·이력·격리·권한·로그 마스킹/한도/장애와 기존 프로젝트·파일·알림 회귀 검사를 포함한다. `api-check` 실제 응답/OpenAPI 검증, `smoke` 16항목, `python -X utf8 scripts/check-external-clients.py` 6개 통과. Docker project-service·admin-web·nginx 빌드 통과, 기존 HLS 청크 크기 경고는 유지한다.
- **실제 연결 검증:** `docker compose -f compose.yml -f compose.dev.yml --profile test run --rm --no-deps external-check start` → DEV project-service/Loki 재시작 → `external-check finish` 통과. 두 테스트 프로젝트에서 키 권한·격리·동시 점유·Python 예제·마스킹·가짜 tenant 거부를 확인하고, 재시작 후 로그 유지·점유 만료·오래된 워커 거부·두 번째 실행 완료까지 검증했다. 만든 키는 폐기하고 해당 프로젝트는 중지했다. 진단 로그는 보존 정책으로 만료되며 실제 사용자 데이터는 변경하지 않았다.

### 모바일 접속 기기 메뉴·실제 IP 전달 수정

- 모바일 계정 헤더의 자동 여백 때문에 점 3개 메뉴가 가운데 놓이던 원인을 수정했다. 프로필 아이콘 옆에 정렬하고 터치 영역을 확보했으며, 접속 기기 이름·로그아웃·상세 정보의 모바일 배치를 보완했다. Keycloak 기본 JavaScript는 유지하고 계정 테마 CSS만 추가했다.
- 공개 도메인 Chromium에서 320/390/768/1440px 정렬·가로 넘침 없음, 메뉴·Escape·포커스 복귀, 320px 기기 로그아웃 버튼 겹침 없음·확인 취소를 검증했다. 실제 iPhone/Android의 화면 배치 검수는 별도 미실행이다.
- IP 문제는 NAS에 5443→NPM 443 DNAT가 있으나 `PREROUTING → DOCKER` 연결이 빠진 점과, 플랫폼이 전달 IP를 Docker 게이트웨이로 덮어쓰던 점을 확인해 수정했다. 사용자가 NAS `192.168.0.93:5443`에만 NAT 연결을 적용했고, 개발 PC에서 직접 접속한 실제 주소·도메인 경로의 공유기 주소가 전달되는 것을 확인했다.
- NPM 기본 사설망 신뢰 때문에 가짜 X-Real-IP가 수용되던 문제도 검사로 발견했다. 해당 도메인의 Advanced에 `set_real_ip_from 127.0.0.1;`을 저장한 뒤 두 경로 모두 위조 거부를 확인했다. 검증 후 플랫폼 `.env`와 Nginx에 `NGINX_TRUSTED_PROXY=172.20.0.1`을 활성화했다. Windows TCP 30140은 NAS만 허용하고 다른 IPv4/IPv6를 차단하는 규칙을 적용했다. 활성 Public 방화벽과 규칙은 확인했으며 다른 LAN 기기의 차단 실측은 미완료다.
- 최종 새 브라우저 로그인에서 내부망 도메인 경로의 `192.168.0.1` 기록·가짜 IP 무시·검사 세션 로그아웃을 확인했다. 사용자는 Wi-Fi를 끈 휴대폰 LTE/5G에서 새 로그인 후 통신사 공인 IP 표시를 확인했다. 기존 세션의 IP는 소급 변경되지 않는다. 진단 로그 설정은 제거하고 사용자 세션은 보존했다.
- Keycloak·Nginx 빌드/반영, 격리 `scripts/check-proxy-ip.sh` 16항목, 최종 smoke 11항목·`nginx -t` 통과. 현재 스택은 `dev`, 7개 컨테이너 healthy다. 공개·직접 경로의 6건 비교는 무시 파일 `output/playwright/probe-nas-ip.py`, 브라우저 검사는 기존 비밀값 비출력 래퍼로 실행했다. 레지스트리 게시·별도 운영 서버 배포는 미실행이다.
- NAS는 헤놀로지·Container Manager, SSH 9022이며 에이전트 키 인증이 없어 사용자가 NAS 명령을 실행했다. NPM Compose·데이터/인증서 볼륨·다른 컨테이너 포트·공유기는 변경하지 않았다. 사용자가 `NPM HTTPS IP Restore` 부팅 작업 등록·수동 실행과 PC 한정 임시 규칙 정리를 완료했다. 제공한 조회 출력에는 `DEFAULT_PREROUTING`의 NAS 5443 연결 규칙 하나만 남았으며, 정리 후 공개·직접 경로 6건 재검사에서 실제 주소 유지·가짜 헤더 무시·Nginx 설정 복구를 확인했다. 부팅 스크립트의 셸 문법 검사는 통과했으며 NAS 재부팅 검증은 미실행이다. 운영 NAS 이동 시 프록시 주소·방화벽을 재검증한다. 설정·검증·되돌리기는 [역방향 프록시 안내](REVERSE_PROXY.md)를 따른다.
- 사용자 요청으로 다른 프로젝트에 독립적으로 복사할 수 있는 [실제 접속 IP 공통 지침](CLIENT_IP_GUIDE.md)을 추가했다. 신뢰 경계·Nginx/NPM 예시·애플리케이션 기록·위조/우회 검증·NAS별 조치 구분과 AGENTS.md 복사용 지침을 담았다. 문서 예시는 배포 템플릿이 아니며 새 프로젝트의 주소·포트·설치 버전에 맞춰 적용·검증한다.

### 운영 관리자 MFA·분실 복구

- `identity-setup`에 운영 관리자 전용 Keycloak 기본 인증 앱·복구 코드 흐름을 추가했다. `platform-admin-mfa-v2`는 비밀번호 뒤에 OTP 또는 일회용 복구 코드를 요구하고, 인증 수단이 없는 계정은 등록을 요구한다. MFA를 완료한 기존 세션은 새로고침 시 유지한다. 운영의 비밀번호 단독 직접 발급을 차단하며 최초 적용 때 기존 세션을 종료한다. 개발 관리자·프로젝트 이용자·master 인증은 유지한다.
- 최초 OTP 등록 뒤 복구 코드 보관을 요구하고, 기존 OTP만 있는 계정도 보완한다. 설정 재실행은 비밀번호·등록된 인증 수단·복구 코드를 보존한다. 별도 인증 흐름과 예상하지 못한 단계는 덮어쓰지 않도록 검사한다. Keycloak의 하위 흐름 생성 API에 맞춰 구성을 보완했고, 미연결 빈 검사 흐름 두 개만 정리했다. 초기 세션 유지 검토를 반영해 최종 v2 흐름에서 로그인·새로고침을 실제 검증했다.
- `admin_security.py recover`는 서버 운영자만 사용하는 명령이다. 대상 관리자 역할과 MFA 흐름 확인 후 로그인 차단·온라인/오프라인 세션 종료·기존 OTP/복구 코드/보안 키 폐기·임시 비밀번호 설정·새 비밀번호와 MFA 재등록 요구·실패 잠금 해제를 수행한다. 중간 실패 시 계정을 다시 열지 않는다. 임시 비밀번호는 새 0600 파일에만 쓰고 기존 파일은 덮어쓰지 않는다. 관리자 이벤트에는 요청 본문을 남기지 않으며 사유와 묶음 결과는 운영자 출력에 기록한다.
- 관리자 화면에 **내 계정** 진입을 추가했다. 초기 관리자 import에 본인 계정 관리 역할이 없어 계정 API가 401을 반환하던 원인을 확인하고 `account`의 `manage-account`·`view-profile`만 추가했다. 다른 사용자·realm 관리 역할은 부여하지 않는다. 복구 코드 경고의 접근성 문구·다운로드 날짜·인쇄 제목도 한국어로 보완했다.
- `python scripts/check-admin-security.py` 통과: 세션 종료/비밀번호 설정 실패 후 차단 유지, 비밀번호 비출력, 기존 파일·필수 동작·이벤트 설정 보존. tools·Keycloak·관리자 웹 빌드와 TypeScript/Vite 검사 통과. dev/prod `identity-setup` 재실행 통과. 재기동 중 실행한 초기화는 연결 실패했고 healthy 복귀 후 통과했다.
- 공개 도메인 Chromium의 임시 운영 관리자에서 최초 인증 앱·복구 코드 등록, 잘못된 OTP 거부·정상 로그인, 사용한 복구 코드 재사용 거부·다음 번호 사용을 확인했다. 실제 운영자 복구 후 기존 비밀번호 거부·임시 비밀번호의 새 비밀번호 설정·새 OTP와 복구 코드 등록까지 완료했다. 최종 v2에서도 OTP·새로고침·복구 코드 검사를 통과했다. 서버에서도 자격증명과 남은 필수 동작 없음, 비밀번호 단독 발급 차단, 본문 없는 복구 감사 이벤트를 확인했다.
- 사용자는 본인 `admin`의 운영 인증 앱 등록·복구 코드 보관을 완료했다고 알려 주었다. 후속 읽기 전용 조회에서는 복구 코드는 존재하지만 OTP 자격증명은 없고, 남은 필수 동작은 없으며 계정은 활성 상태였다. 따라서 인증 앱 등록 완료는 서버에서 확인되지 않았다. 사용자가 비밀번호만으로 로그인하는 방법을 문의해 개발 관리자는 가능하며, 운영은 복구 코드 삭제가 아니라 MFA 정책 변경이 필요하다고 안내했다. 정책·인증 수단은 변경하지 않았다. 현재 스택 모드는 계속 `dev`, 운영 인증 흐름은 `platform-admin-mfa-v2`다. 본인 QR·OTP 비밀키·복구 코드 원문은 출력·보관하지 않았다. 사용 절차는 [관리자 보안 안내](ADMIN_SECURITY.md)를 따른다.
- 최종 **내 계정** 브라우저 검사는 현재 dev 관리자 realm 이동·한국어 내 정보·1440/390px 헤더와 가로 넘침 없음을 통과했다. 초기 검사 코드의 기동 완료 대기·계정 주소 끝 슬래시 처리를 실제 동작에 맞췄다. 실제 운영 CLI 비밀번호 발급 요청은 `400 unauthorized_client`로 차단됐다. 최종 smoke 11항목 통과. 임시 `mfa-check-` 관리자만 비활성화하고 세션을 종료했으며 프로필은 보존했다. 검사 비밀번호·OTP·복구 코드가 담긴 로컬 fixture와 임시 비밀번호 파일은 검수 후 삭제한다.
- 관리자 브라우저 로그아웃과 검사 비밀번호·OTP·복구 코드 fixture, 임시 비밀번호 파일 삭제까지 완료했다. 현재 개발 스택을 유지하며 새로운 상시 프로세스는 없다. 이미지 레지스트리 게시·별도 운영 서버 배포는 이번 검증에 포함하지 않았다.

### 환경별 회원·세션 관리 구현 — 새 Windows PC 검증

- 환경별 회원 목록·부분 검색·페이지 이동·상세·연결된 소셜 제공자, 활성화/비활성화와 온라인 세션 조회·개별/전체 종료를 추가했다. 관리자 JWT만 허용하며 다른 프로젝트·환경·회원의 세션 접근을 차단한다. 기술용 서비스 계정은 일반 회원 조회·조작에서 제외한다.
- Keycloak을 회원 정보 원본으로 유지한다. 비활성화는 계정을 먼저 막은 뒤 온라인·오프라인 세션을 종료하고 프로필·연결·동의 설정은 보존한다. 종료 오류가 나도 계정을 다시 열지 않는다. 중지 프로젝트는 조회·비활성화·세션 종료를 허용하며 활성화는 차단한다. 기존 접근 토큰을 자체 검증하는 서비스에서 만료 전 즉시 차단을 보장하지 않는 한계를 화면에 표시한다.
- 현재 상태 확인과 프로젝트 잠금으로 플랫폼의 동시 변경 충돌을 검사한다. 감사 이력에 환경·회원·선택 세션과 성공/실패를 기록한다. V5·V6는 감사 문맥과 Keycloak의 UUID가 아닌 세션 식별자를 지원한다. 개발 DB에 먼저 적용한 V5는 변경하지 않고 V6에서 타입을 변환해 기존 이력을 보존했다.
- 새 PC에는 기존 플랫폼 컨테이너·볼륨이 없었다. 기존 `.env`를 보존해 새 DB와 개발 스택을 초기화했다. 처음 localhost에서 검증한 뒤 사용자 지시에 따라 `https://platform.shnea.kr`로 공개 주소·관리자 콜백을 복구했다. 운영 모드는 계속 `dev`다. 새 DB에는 이전 PC의 실제 소셜 로그인 검수 계정이 없으며 이번 전용 검증 계정만 있다.

## 가입·계정 복구 정책

- 사용자 승인에 따라 기존 일반 가입 설정과 별도로 이메일 로그인·이메일 인증·비밀번호 재설정·최소 길이 관리 API와 화면을 추가했다. Keycloak을 설정 원본으로 사용하며 감사 이력과 revision 충돌 검사를 제공한다.
- 기존 환경의 정책·계정·비밀번호·세션은 자동 변경하지 않는다. 새 환경은 기본 12~128자이며 최소 길이를 12~128자로 설정할 수 있다. Keycloak의 별도 규칙은 덮어쓰지 않는다. 일반 가입·콜백 변경과 중지·재개 때 추가 정책을 보존한다.
- 이메일 인증·복구는 운영 모드·PROD·Keycloak 이메일 설정이 있을 때만 켤 수 있다. 현재는 SMTP host/from의 존재를 확인하며 실제 발송 성공을 뜻하지 않는다. NCP 발송 연동·개발 모의 수신함·실제 이메일 복구 검수는 남아 있다.
- Docker 프로젝트 서비스 JUnit 8개와 관리자 TypeScript·Vite 빌드 통과. `check-authentication-policy.py`에서 관리자 경계·입력 검증·실제 비밀번호 길이 제한·동시 저장 200/409·수동 규칙 보호·가입 설정 보존·중지 유지·감사 이력을 확인했다.
- 최소 길이 128에서도 개발 Mock이 동작하도록 내부 임시 비밀번호를 128자로 변경하고 해당 조건을 검사했다. 외부 이메일·소셜 로그인은 호출하지 않았다. 검사 사용자 삭제·키 폐기 후 `policy-check-4451f27522`, `policy-check-d9a1c3e173` 프로젝트를 중지 상태로 남겼다.

- 실제 브라우저에서 정책 저장·재조회·이메일 활성화 차단과 1440px/390px 배치를 확인했다. 모바일 가로 넘침 없으며 UI 검사 도구의 새 지적은 없었다. 최초 브라우저 검사는 관리자 세션 만료로 멈췄고 로컬 관리자 재로그인 후 통과했다. 이번 화면 검수는 어두운 테마에서 수행했다.

## 이전 단계: 소셜 설정 관리와 Keycloak 연결 코드

아래는 개별 키·콜백을 사용하던 단계의 기록이며 현재 방식은 상단 공통 소셜 콜백 설명을 따른다.

- 구글·카카오·네이버의 프로젝트·환경별 설정 조회·저장, 비밀키 유지/교체, 콜백 안내와 활성화 설정을 추가했다. 구글은 기본 제공자, 카카오는 OIDC, 네이버는 새 Gradle 기반 Keycloak 확장을 사용한다.
- 관리 API는 관리자 JWT만 허용한다. 소셜 비밀값 원본은 Keycloak에만 두고 응답에는 등록 여부만 제공한다. 플랫폼 DB에는 비밀값 없는 감사 이벤트를 남긴다. 미소유 별칭을 덮어쓰지 않고, 환경 READY 검사·프로젝트 잠금·revision으로 충돌을 차단한다.
- 개발 모드·DEV는 실제 소셜 활성화를 차단하며 Mock을 유지한다. 운영 모드의 PROD만 실제 활성화 가능하다. 중지 프로젝트도 설정 편집은 가능하지만 realm은 중지 상태를 유지한다.
- 기본 첫 소셜 로그인 흐름을 사용하고 이메일 자동 신뢰·토큰 저장을 끈다. 카카오 서명·issuer·JWKS 검증과 PKCE(S256)를 구성했다. 네이버는 Keycloak의 state 검증 이후 토큰 요청에도 state를 전달하고, 프로필 응답 코드·고유 ID를 검사한다.
- Docker에서 프로젝트 서비스 JUnit 6개, 네이버 확장 JUnit 2개·이미지 빌드, 관리자 TypeScript·Vite 빌드를 통과했다. 초기 확장 검사에서 테스트용 제공자를 활성화하지 않은 문제와 JAR 소유권 문제를 수정했다.
- `check-social-settings.py` 통과: 관리자 경계·필수 입력·개발 활성화 차단·세 제공자 설정·비밀키 마스크 유지·새 앱 키의 비밀키 요구·콜백·revision·동시 저장 200/409·realm 재반영/중지 시 설정 보존·감사 비밀값 비노출. 실제 소셜 로그인은 호출하지 않았다. 검사 키는 폐기하고 가짜 소셜 설정은 삭제했다. `social-settings-714c92b945` 프로젝트는 중지 상태로 남긴다.
- smoke 통과: 상태 URL·관리자 HTML/보안 헤더·외부 진단 차단·Keycloak issuer. 개발 컨테이너 7개는 실행 상태다.
- 브라우저에서 세 제공자 선택·콜백·개발 활성화 차단을 확인했다. 저장 응답은 브라우저 모의 응답으로 확인했고, 필수 비밀키·저장 후/실패 후 입력 초기화·앱 키 변경·저장 안내 초기화·409 오류·조회 503과 재시도 복구를 확인했다. 새로고침 응답 전 검사하던 자동화 대기를 보완했다. 콘솔의 새 409/503 두 건은 의도한 오류 주입이며 새 JavaScript 오류는 없었다.
- 1440px 데스크톱·390px 모바일과 밝은/어두운 테마를 확인했다. 가로 넘침 없음, 체크박스 정렬 수정 후 18px 크기를 확인했고 UI 검사 도구의 새 지적은 없었다.
- **실제 구글·카카오·네이버 로그인은 미검증.** 사용자가 인증 정보를 추후 보강하고 테스트도 나중에 진행하기로 했다. 기존 소셜 앱·키·콜백은 변경하지 않았다. 사용법은 ADMIN_WEB.md, API와 실패 후 재조회 규칙은 PROJECT_API.md에 기록했다.

## 개발 로그인 테스트 화면과 실패 시나리오

- DEV 환경에 카카오·네이버·구글 제공자, 테스트 사용자 ID, 성공·취소·동의 거부·제공자 장애 선택 폼을 추가했다. PROD에서는 숨기며 중지·미반영 상태에서는 실행할 수 없다.
- 관리자 JWT 전용 `/api/v1/admin/environments/{id}/mock-login`은 안전한 결과 메타데이터만 반환한다. 서버 API 키 입력이 필요 없고 관리자 응답에 이용자 토큰을 포함하지 않는다.
- 기존 `/api/v1/dev/login`에 선택적 `scenario`를 추가했다. 생략 시 기존 성공 흐름을 유지한다. 실패는 403/503을 반환하며 Keycloak 호출·사용자 생성/변경·토큰 발급 없이 감사 기록을 남긴다. 키 권한·폐기·만료·프로젝트 상태 검사를 먼저 수행한다.
- 두 진입점은 같은 실행 로직과 프로젝트 잠금을 사용한다. 운영 모드에는 두 경로를 가진 컨트롤러 자체가 등록되지 않는다. 성공 응답에는 안정적인 `userId`와 `scenario`를 추가했다.
- Docker Gradle 테스트·빌드, TypeScript·Vite 빌드 통과. `check-mock.py`에서 관리자 경계·토큰 비노출·세 제공자·반복 사용자·실패 상태·사용자 미생성·권한 부족·PROD/중지 차단·감사 이력을 검증했다. `check-lifecycle.py` 회귀 검사도 통과했다.
- 임시 prod 모드 컨테이너에서 `check-prod-mode.py` 통과: 개발 JWT 거부·Mock API 404. 검증 후 임시 컨테이너를 종료했다.
- 실제 브라우저에서 세 제공자 성공·세 실패 시나리오·입력 검증·결과 지우기·PROD 미노출·입력/환경 변경 시 결과 초기화·진행 중 늦은 응답 격리를 확인했다. 실제 502 오류는 실패 재현 결과와 구분해 표시한다. 오류 주입에 따른 콘솔 502는 예상된 기록이다.
- 1440px 데스크톱·390px 모바일, 어두운/밝은 테마와 가로 넘침 없음을 확인했다. UI 검사 도구의 새 지적은 없었다. API 검사 키는 폐기했으며 `mock-check-...` 프로젝트는 중지 상태로 보존한다. 브라우저 검증은 기존 `check-...` 프로젝트의 `ui-mock-user`로 실행했다.
- 결과 지우기는 화면 초기화만 한다. 테스트 사용자 일괄 삭제·발송 Mock·실제 소셜 리다이렉트와 콜백 검증은 남아 있다.

## API 키별 기능 권한

- 발급 창에서 연동 정보 조회(`integration:read`)와 개발용 가짜 로그인(`auth:mock`) 권한을 선택한다. 새 키는 조회 권한만 기본 선택하며 만료 없음·선택 만료일을 함께 지원한다.
- 환경별 허용 권한 목록 API를 추가했다. 플랫폼 개발 모드의 DEV 환경에서만 Mock 권한을 발급할 수 있다. 빈 배열·중복·알 수 없는 권한·와일드카드는 거부한다.
- 키 검증 공통 경로에서 기능 권한을 검사한다. 유효한 키의 권한 부족은 403, 만료·폐기·중지·환경 미반영은 401이다. 관리자 API 권한을 부여하지 않는다.
- V4는 기존 키가 사용하던 권한만 기록하며 해시·만료일·폐기 상태를 바꾸지 않는다. 목록은 기존 날짜 필드명과 JDBC 날짜 응답 형식을 유지하고 `scopes`를 추가했다.
- 권한 변경은 새 키 발급·연결 서비스 교체·기존 키 폐기로 처리한다. 파일·알림 권한은 해당 API를 구현할 때 추가하며 기존 키에 자동 부여하지 않는다.
- Docker Gradle 테스트·빌드와 관리자 TypeScript·Vite 빌드 통과. `project-check`에서 기존 격리·세 Mock 제공자·PROD 권한 발급 차단을 검증했고, `check-lifecycle.py`에서 조회 전용/Mock 전용 키의 상호 차단·기본값·오류 입력·폐기·만료·프로젝트 중지/재개를 검증했다.
- 실제 V4 SQL을 임시 테이블에 적용해 무기한·유기한·만료·폐기된 키의 원래 데이터 보존과 DEV/PROD 권한을 확인하고 롤백했다. 최초 전후 응답 비교에서 날짜 직렬화 차이를 발견해 기존 응답 형식을 유지하도록 수정했다.
- Playwright에서 권한 기본값·미선택 오류·발급·목록·폐기·선택 만료일·PROD Mock 항목 미노출, 실제 403을 확인했다. 1440px 데스크톱·390px 모바일, 어두운/밝은 테마를 확인했다. UI 검사 도구의 새 지적 사항은 없었다.
- 최종 보완 후 lifecycle 검사를 다시 통과했다. 첫 권한 항목의 키보드 포커스·Escape 복귀, 권한 목록 503 시 발급 차단과 재시도 복구를 확인했다. 이 오류 주입에 따른 브라우저 503 콘솔 기록은 예상된 결과다. 브라우저·마이그레이션 검증용 키는 폐기했다.

## API 키 기본 만료 정책 변경

- 새 서버 API 키는 기본 만료 없음이며, 발급 창/API에서 선택적으로 미래 만료일시를 지정할 수 있다. 만료 없음은 응답·목록에 null 만료일을 반환한다. 관리자 화면은 만료 없음으로 표시하며 폐기할 수 있다.
- V3 마이그레이션으로 만료일을 nullable로 변경한다. 기존 발급 키의 만료일·폐기 상태는 보존한다. 폐기·프로젝트 중지·환경 미반영 차단과 로그인 JWT 만료 정책은 유지한다.
- Docker에서 project-service의 Gradle 테스트·빌드와 admin-web의 TypeScript 검사·Vite 빌드를 통과하고 개발 컨테이너에 적용했다.
- `docker compose -f compose.yml -f compose.dev.yml --profile test run --rm project-check python /checks/check-lifecycle.py` 통과. 기본 무기한 키, 선택 만료일, 잘못된 날짜 거부, 지정 시점 이후 API·Mock 호출 차단, 폐기·중지·재개 흐름을 검증했다.
- Playwright로 기본 무기한 발급·표시·폐기, 과거 날짜 입력 거부, 선택한 기기 시간대의 만료일이 UTC로 전달되는지, 발급 창을 다시 열면 기본값으로 돌아오는지 확인했다. 모바일 390px에서 발급 창 넘침도 확인했다. 검증용 발급 키는 폐기했다.

## 실행 기반 검증 이력

- macOS 호스트의 Linux arm64 Docker에서 Gradle 서비스 이미지 3개 빌드 성공. Java 소스 컴파일·실행 JAR 패키징을 확인했다. 당시에는 Java 테스트가 없어 test 작업이 NO-SOURCE였다. 현재는 위의 프로젝트 서비스 검사를 추가했다.
- Compose 설정 검사: 운영 구성에 build·소스 마운트가 없고 API·Keycloak·DB 호스트 포트 미노출, 자원 제한 조정 가능, 비밀값 누락 시 실패 확인.
- 환경 생성기: 비밀번호 6개가 서로 다름, 파일 권한 0600, 기존 파일 보존 확인.
- `docker compose -f compose.yml -f compose.dev.yml --profile test run --rm db-check`: 자기 DB와 스키마 접근 4건 성공, 타 서비스 DB 접속 12건 차단.
- `docker compose -f compose.yml -f compose.dev.yml --profile test run --rm smoke`: 상태 URL 4개, 외부 진단 경로 차단, 내부 Actuator 제한, Keycloak 고정 issuer·전달 헤더 위조 검사 통과.
- 새 플랫폼 DB만 중지한 뒤 `smoke python /checks/smoke.py --db-down`: Nginx는 정상, API readiness 3개는 HTTP 503으로 DB 장애 표시.
- DB 재기동 후 Compose의 6개 컨테이너가 모두 healthy로 복구되는 것을 확인했다.
- 첫 기동 중 확인한 Keycloak 빌드 시 경로 설정 누락을 수정했다. 개발 DB의 내부 네트워크만으로 포트가 열리지 않는 문제는 개발 전용 브리지 추가로 수정하고 127.0.0.1:30141 배정을 확인했다.
- Gradle 빌더의 linux/amd64·linux/arm64 이미지 manifest 확인. Windows 개발·Linux amd64 실제 기동과 운영 배포는 아직 검증하지 않았다.

## 재개와 실행 환경

다른 PC의 복제·초기화·별도 준비 항목과 다음 대화용 요청은 [작업 인계 안내](HANDOFF.md)에 정리했다. 코드·문서는 Git으로 이동하며 실제 `.env`와 Docker DB 볼륨은 별도다. 새 PC에서 개발 DB를 새로 생성해 이어갈 수 있다. 이번 PC 이동 준비에서는 데이터 백업이나 이미지 레지스트리 게시를 수행하지 않았다.

```sh
git status --short --branch
git log -5 --oneline
git fetch origin
docker compose -f compose.yml -f compose.dev.yml ps
```

개발 Compose 프로젝트 이름은 `.env`의 `shnea-platform-dev`다. 다른 기존 컨테이너와 볼륨을 사용하지 않는다. `.env`는 Git에서 제외되므로 다른 PC에서는 생성기를 실행한다. DB 데이터가 이미 있는 환경에서는 `.env`만 새로 생성하지 말고 기존 자격증명과 일치시켜야 한다.

검증 후 개발 컨테이너 7개는 실행 상태로 둔다. 현재 PC의 접속 주소는 https://platform.shnea.kr 이며 통합 관리자 UI, 프로젝트·인증 API와 Keycloak 기본 관리 화면을 제공한다. [관리자 화면 안내](ADMIN_WEB.md)를 따른다. 플랫폼 계정은 admin, 비밀번호는 .env의 PLATFORM_ADMIN_PASSWORD이며 master 계정과 별개다.

실행: `docker compose -f compose.yml -f compose.dev.yml up -d --build --wait --wait-timeout 300`.
중지: `docker compose -f compose.yml -f compose.dev.yml down`. DB 볼륨은 보존한다.

최신 커밋·푸시 여부는 Git에서 확인한다. `ahead`이면 미푸시 커밋을 확인해 검증 후 푸시한다. 원격 분기가 있으면 사용자 변경을 보존한다.
