# 운영 알림 조회·확인

주요 메뉴의 **운영 알림**에서 프로젝트·환경을 선택한다. 프로젝트의 **개요 → 알림 보기**에서도 선택 범위를 유지해 이동한다. 현재는 알림 서비스가 수신한 `job.failed` 이벤트의 최종 실패 기록만 다룬다. 서비스 장애·디스크·적체 임계값, 외부 수신 채널, 복구 알림은 후속 범위다. [관리자 화면 탐색](ADMIN_NAVIGATION.md)을 참고한다.

## 화면 사용

- 기본 필터는 **미확인**이다. 확인됨·전체로 바꾸거나 **알림 새로고침**으로 다시 조회한다. 환경별 20개씩 표시하며 이전·다음 페이지를 제공한다. 자동 조회는 하지 않는다.
- 알림에는 실패 설명·발생/수신 시각을 표시한다. **알림 상세·확인 기록**을 펼치면 알림 ID, Job ID, 실패 코드, 작업 요청 ID와 최초 확인 관리자·시각·요청 ID를 볼 수 있다.
- **알림 확인 처리**에서 환경과 대상을 확인한 뒤 실행한다. ‘확인됨’은 읽고 인지했다는 뜻이다. 원래 Job 상태를 바꾸거나 문제 해결·재시도·이벤트 재전송을 수행하지 않는다.
- 이미 확인된 알림에 반복 요청하거나 여러 관리자가 동시에 확인해도 최초 확인 기록을 보존한다. 이벤트가 중복 수신돼도 다시 미확인으로 돌아가지 않는다. 확인 취소는 제공하지 않는다.
- 조회 실패 시 이전 목록을 숨긴다. 확인 결과를 확정하지 못하면 같은 창의 재제출을 막으므로 닫은 뒤 새로고침해 상태를 먼저 확인한다. 확인 창을 닫으면 운영 알림 제목으로 포커스를 돌린다.

## API·권한

| API | 동작 |
| --- | --- |
| `GET /api/v1/admin/environments/{id}/operational-alerts` | `acknowledged` 생략=전체, `false`=미확인, `true`=확인됨. `limit` 기본 20·최대 100, `offset` 0~1,000,000. 수신 시각 최신순 |
| `POST /api/v1/admin/environments/{id}/operational-alerts/{eventId}/acknowledge` | 본문 없음. 최초 확인 또는 기존 확인 기록 반환(200). 다른 환경의 알림·없는 알림은 404 |

두 API는 관리자 JWT 전용이다. 서버 API 키·일반 회원에게 열지 않는다. 프로젝트 서비스는 자기 DB에서 환경의 프로젝트를 찾고 내부 HTTP로 알림 서비스에 요청한다. 브라우저가 프로젝트 범위나 확인 관리자 ID를 지정하지 못한다. 중지된 프로젝트의 과거 알림도 조회·확인할 수 있다.

내부 `/internal/v1/operational-alerts`와 `/{id}/acknowledge`는 `PLATFORM_EVENTS_SECRET`으로 인증하며 외부 Nginx에는 공개하지 않는다. 이메일 키로 접근할 수 없다. 프로젝트/환경 UUID는 둘 다 필수이며 확인 처리는 두 범위가 일치하는 알림에만 허용한다. 내부 서비스 장애는 외부 API에서 공통 502 오류로 안내한다.

## 기록과 검증

알림 데이터는 알림 서비스 DB에 남는다. `alert_acknowledgements`의 이벤트 ID 유일성 제약·행 잠금으로 최초 관리자, 시각, 요청 ID를 한 번만 저장한다. 이 행이 확인 처리의 감사 기록이며 알림 상세에서 조회한다. 프로젝트 서비스의 기존 감사 메뉴와 통합한 조회는 후속 작업이다. 다른 서비스 DB를 직접 읽거나 두 DB에 이중 기록하지 않는다.

기존 알림은 V3 마이그레이션 후 모두 미확인 상태로 조회된다. 별도 보존 기간·자동 삭제는 아직 없다. 알림 서비스 → 프로젝트 서비스 → 관리자 웹 순서로 갱신한다.

```powershell
docker compose -p platform-job-checks -f compose.jobs-test.yml up --abort-on-container-exit --exit-code-from check
docker compose -p platform-job-checks -f compose.jobs-test.yml down
```

격리 검증은 실제 PostgreSQL에서 프로젝트/환경 격리, 필터·페이지 제한, 동시/반복 확인, 최초 기록 보존, 확인 저장 실패를 검사한다. 내부 HTTP·보안 필터는 전용 키, 관리자 JWT 경계, 입력 검증, 서버에서 결정한 범위·관리자 전달을 검사한다.

실제 DEV API는 아래 명령으로 확인한다. `job-check-`로 시작하는 중지된 검수 프로젝트에서 **이미 확인한 알림**의 UUID를 사용한다. 새 알림을 확인하거나 Job을 실행하지 않으며, 반복 확인이 최초 기록을 바꾸지 않는지 검사한다. 자체 관리자 로그인 세션은 검사 후 종료한다.

```powershell
docker compose -f compose.yml -f compose.dev.yml --profile test run --rm --no-deps api-check python /checks/check-alerts-api.py --environment <검수-환경-UUID> --alert <확인된-알림-UUID>
```

실제 응답 스키마, 확인 상태 필터, 최초 확인 기록 보존, 잘못된 입력·비로그인·없는 대상의 400/401/404를 검사한다. 동시성·다른 프로젝트/환경 격리·403은 위 격리 서버 검사 범위다.
