# 운영 알림·이메일 수신 설정

주요 메뉴의 **운영 알림**에서 프로젝트·환경을 선택한다. 프로젝트의 **개요 → 알림 보기**에서도 선택 범위를 유지해 이동한다. **알림 목록·수신 설정·발송 이력**으로 나뉘며 환경 반영 Job의 최종 실패·복구와 대기 적체·해소·감시 종료를 다룬다. 적체 조건은 모니터링의 **적체 경보 설정**에서 관리한다. 서비스 장애·디스크, 이메일 외 채널은 후속 범위다. [관리자 화면 탐색](ADMIN_NAVIGATION.md)을 참고한다.

## 화면 사용

- 기본 필터는 **미확인**이다. 확인됨·전체로 바꾸거나 **알림 새로고침**으로 다시 조회한다. 환경별 20개씩 표시하며 이전·다음 페이지를 제공한다. 자동 조회는 하지 않는다.
- 알림에는 실패 설명·발생/수신 시각을 표시한다. **알림 상세·확인 기록**을 펼치면 알림 ID, Job ID, 실패 코드, 작업 요청 ID와 최초 확인 관리자·시각·요청 ID를 볼 수 있다.
- **알림 확인 처리**에서 환경과 대상을 확인한 뒤 실행한다. ‘확인됨’은 읽고 인지했다는 뜻이다. 원래 Job 상태를 바꾸거나 문제 해결·재시도·이벤트 재전송을 수행하지 않는다.
- 이미 확인된 알림에 반복 요청하거나 여러 관리자가 동시에 확인해도 최초 확인 기록을 보존한다. 이벤트가 중복 수신돼도 다시 미확인으로 돌아가지 않는다. 확인 취소는 제공하지 않는다.
- 조회 실패 시 이전 목록을 숨긴다. 확인 결과를 확정하지 못하면 같은 창의 재제출을 막으므로 닫은 뒤 새로고침해 상태를 먼저 확인한다. 확인 창을 닫으면 운영 알림 제목으로 포커스를 돌린다.

## 이메일 수신과 복구

최종 실패(`JOB_FAILED`)와 대기 적체(`JOB_BACKLOGGED`)는 서로 다른 종류다. 같은 환경이어도 두 종류의 이메일 억제·해소를 섞지 않는다. 아래 환경 반영 성공 규칙은 최종 실패에 적용하며 적체는 다음과 같이 구분한다.

- `JOB_BACKLOGGED`: 설정한 대기 기준을 연속 초과했다. 열린 사건은 한 번만 생성하며 정기 재알림은 없다.
- `JOB_BACKLOG_RECOVERED`: 해당 작업이 적체 기준에서 벗어난 것을 연속 확인했다. 작업 성공을 보장하지 않으며 최종 실패 알림을 복구하지 않는다.
- `JOB_BACKLOG_CLOSED`: 설정을 바꾸거나 꺼서 감시를 종료했다. 실제 해소가 아니며 복구 이메일을 보내지 않는다. 원래 적체에 ‘감시 종료됨’을 표시한다.

발생과 해소/종료를 사건 ID로 연결하며 역순 수신도 원래 기록을 보존한다. 종료 수신 시 원래 적체의 아직 PENDING인 이메일은 취소하지만, 서비스 사이 전달 지연 중 이미 시작한 발송은 회수할 수 없다. `resolutionType`으로 실제 해소와 종료를 구분한다. [모니터링 지침](MONITORING.md)에 조건·검사 간격·공백 처리·설정 API를 정리했다.

- **수신 설정**에서 이메일 주소 1개, 같은 실패의 이메일 간격(1~1,440분, 기본 15분), 복구 이메일 여부를 저장한다. 기본은 꺼짐이며, 저장 뒤 들어오는 이벤트부터 적용한다. 설정을 켜도 과거 알림을 다시 보내지 않는다. 확인창에서 환경·주소·변경 효과를 확인한다.
- `dev/DEV`는 외부 이메일 없이 **모의 발송**, `prod/PROD`는 NCP 키·발신 주소가 준비된 경우에만 실제 발송한다. 다른 조합과 준비되지 않은 경로는 차단한다. 프로젝트가 중지돼도 장애를 인지할 수 있도록 운영 알림 설정·처리는 유지한다. 인증 이메일의 활성 환경 제한과는 별도 정책이다.
- 같은 프로젝트·환경의 미복구 Job 실패는 하나의 장애 흐름으로 묶어 이메일만 억제한다. 시간은 이벤트 수신 후 발송 대기에 등록한 시각부터 센다. 실패 코드가 달라도 같은 환경이면 억제하며, 기간 안의 마지막 실패를 나중에 예약 발송하지 않는다. 기간 경과 후 새 실패가 들어오면 다시 알린다. 모든 실패는 알림 목록에 남고 상세에 생략 이유를 표시한다.
- `targetRevision`(환경 설정 버전), `occurredAt` 순서로 비교한다. 이후의 `job.succeeded`는 이전 실패에 복구 이벤트 ID를 연결하고 `JOB_RECOVERED` 알림을 만든다. 같은 버전·같은 시각의 성공만으로는 복구를 선언하지 않는다. 취소는 복구로 보지 않는다. 과거 성공·실패의 지연 수신은 현재 장애에 대한 이메일을 보내지 않는다. 성공이 먼저 도착한 뒤 과거 실패가 오면 그 실패에 복구 이벤트를 연결하되 복구 메일을 뒤늦게 생성하지 않는다.
- 복구는 해당 버전의 **환경 반영 성공**을 뜻하며 전체 서비스 정상 여부를 보장하지 않는다. 원래 실패 Job과 읽음 확인 기록은 보존한다. 복구 이메일을 꺼도 복구 기록은 남긴다. 복구 후의 새 실패는 직전 발송 간격과 무관하게 알린다.
- 설정을 바꾸면 변경 전 `PENDING`을 취소한다. 이미 `SENDING`인 이메일은 회수하지 않는다. 설정 버전이 다르면 409 `SETTINGS_CHANGED`로 거부하며 새로고침 후 다시 저장한다. 변경 감사는 알림 DB의 `alert_email_settings_audit`에 버전별 스냅샷·관리자·요청 ID·시각을 보관한다. 화면은 최근 변경을 보여 주며 전체 감사 메뉴 연결은 아직 없다.

**발송 이력**은 환경별 20개씩 수동 조회한다. 생략된 이메일은 발송 행을 만들지 않고 알림의 `emailDecision`으로 구분한다.

| 상태 | 뜻 |
| --- | --- |
| `PENDING` / `SENDING` | 발송 대기 / 발송 시도 중 |
| `MOCK` | DEV에서 외부 요청 없이 처리 |
| `ACCEPTED` | NCP 요청 ID로 접수를 확인함. 실제 수신함 도착·열람을 뜻하지 않음 |
| `FAILED` | 발송사가 4xx로 거부함 |
| `UNKNOWN` | 시간 초과·5xx·확인할 수 없는 응답·발송 중 중단. 자동 재전송 없음 |
| `CANCELLED` | 수신 설정 변경 또는 적체 감시 종료로 이전 발송 대기를 취소함 |
| `BLOCKED` | 처리 시점의 환경·NCP 경로가 허용되지 않음 |

발송 워커는 기존 알림 서비스 내부에서 기본 3초마다 최대 10건을 처리한다. DB에서 한 행을 독점 점유해 `SENDING`으로 먼저 커밋한 뒤 외부 요청을 한 번만 시도한다. 2분 넘게 남은 `SENDING`은 `UNKNOWN`으로 바꾸며, 재시작해도 다시 보내지 않는다. 이 방식은 중복 시도를 줄이지만 외부 요청 전 프로세스가 중단되면 미발송 상태로 끝날 수 있다. NCP 요청 ID와 알림 ID로 별도 확인하고 결과 불명 요청을 임의로 재전송하지 않는다. 실패·불명·차단 모두 자동 재시도와 수동 재발송 기능은 아직 없다. 서비스 중지는 기존 Compose 방식이며 다른 알림 수신도 함께 중지된다.

## API·권한

| API | 동작 |
| --- | --- |
| `GET /api/v1/admin/environments/{id}/operational-alerts` | `acknowledged` 생략=전체, `false`=미확인, `true`=확인됨. `limit` 기본 20·최대 100, `offset` 0~1,000,000. 수신 시각 최신순 |
| `POST /api/v1/admin/environments/{id}/operational-alerts/{eventId}/acknowledge` | 본문 없음. 최초 확인 또는 기존 확인 기록 반환(200). 다른 환경의 알림·없는 알림은 404 |
| `GET /api/v1/admin/environments/{id}/operational-alerts/email-settings` | 미설정이면 기본 꺼짐·revision 0. 현재 발송 경로와 최근 변경 기록 |
| `PUT /api/v1/admin/environments/{id}/operational-alerts/email-settings` | `enabled`, `recipient`, `suppressionMinutes`, `recoveryEnabled`, `revision` 필수. 변경 후 설정 반환 |
| `GET /api/v1/admin/environments/{id}/operational-alerts/email-deliveries` | `limit` 1~100·기본 20, `offset` 0~1,000,000. 접수 최신순·수신 주소·상태·처리 시각·발송사 요청 ID |

모든 API는 관리자 JWT 전용이다. 서버 API 키·일반 회원에게 열지 않는다. 프로젝트 서비스는 자기 DB에서 환경의 프로젝트·DEV/PROD 종류를 찾고 내부 HTTP로 알림 서비스에 요청한다. 브라우저가 프로젝트 범위나 확인 관리자 ID를 지정하지 못한다. 중지된 프로젝트의 과거 알림도 조회·확인할 수 있다.

내부 `/internal/v1/operational-alerts`, `/{id}/acknowledge`, `/email-settings`, `/email-deliveries`는 `PLATFORM_EVENTS_SECRET`으로 인증하며 외부 Nginx에는 공개하지 않는다. 이메일 키로 접근할 수 없다. 프로젝트/환경 UUID는 둘 다 필수이며 확인 처리는 두 범위가 일치하는 알림에만 허용한다. 내부 서비스 장애는 외부 API에서 공통 502 오류로 안내한다.

## 기록과 검증

알림 데이터는 알림 서비스 DB에 남는다. `alert_acknowledgements`의 이벤트 ID 유일성 제약·행 잠금으로 최초 관리자, 시각, 요청 ID를 한 번만 저장한다. 이 행이 확인 처리의 감사 기록이며 알림 상세에서 조회한다. 프로젝트 서비스의 기존 감사 메뉴와 통합한 조회는 후속 작업이다. 다른 서비스 DB를 직접 읽거나 두 DB에 이중 기록하지 않는다.

기존 알림은 V3 마이그레이션 후 모두 미확인 상태로 조회된다. V4는 기존 성공 이벤트로 과거 실패의 복구 연결만 계산하며, 과거 이메일·복구 알림을 일괄 생성하지 않는다. 기존 확인 기록은 보존한다. 이메일 본문은 DB에 저장하지 않으며 환경·Job·알림 UUID와 상태 안내만 생성한다. 수신 주소는 설정·변경 감사·발송 이력에 저장하므로 관리자 전용으로 조회한다. 별도 보존 기간·자동 삭제는 아직 없다. 알림 서비스 → 프로젝트 서비스 → 관리자 웹 순서로 갱신한다.

```powershell
docker compose -p platform-job-checks -f compose.jobs-test.yml up --abort-on-container-exit --exit-code-from check
docker compose -p platform-job-checks -f compose.jobs-test.yml down
```

격리 검증은 실제 PostgreSQL에서 프로젝트/환경 격리, 필터·페이지 제한, 동시/반복 확인, 최초 기록 보존, 확인 저장 실패, 동시 실패·중복 억제 만료·복구 후 재실패·순서 역전·설정 동시 변경·발송 독점 점유·중단 후 UNKNOWN·모의 외부 발송 차단·큐/감사 실패 롤백을 검사한다. 내부 HTTP·보안 필터는 전용 키, 관리자 JWT 경계, 입력 검증, 서버에서 결정한 범위·관리자 전달을 검사한다. NCP는 모의 클라이언트를 사용하며 실제 수신함 전달·실제 OS 프로세스 종료 검수는 별도다.

실제 DEV API는 아래 명령으로 확인한다. `job-check-`로 시작하는 중지된 검수 프로젝트에서 **이미 확인한 알림**의 UUID를 사용한다. 새 알림을 확인하거나 Job을 실행하지 않으며, 반복 확인이 최초 기록을 바꾸지 않는지 검사한다. 자체 관리자 로그인 세션은 검사 후 종료한다.

```powershell
docker compose -f compose.yml -f compose.dev.yml --profile test run --rm --no-deps api-check python /checks/check-alerts-api.py --environment <검수-환경-UUID> --alert <확인된-알림-UUID>
```

실제 응답 스키마, 확인 상태 필터, 최초 확인 기록 보존, 잘못된 입력·비로그인·없는 대상의 400/401/404를 검사한다. 동시성·다른 프로젝트/환경 격리·403은 위 격리 서버 검사 범위다.
