PLATFORM · OPERATIONS GUIDE

코드를 올리면,
검증 후 NAS에 배포됩니다.

GitHub 서버가 테스트와 이미지 빌드·게시를 마치면, NAS의 배포 전용 Runner가 작업을 받아 완성된 이미지를 실행합니다. 외부 접속 국가 제한은 유지합니다.

GitHub에서 배포 결과 보기 ↗운영 서비스 열기 ↗상태 확인 명령
배포 흐름평소 사용법상태·로그실패·복구폴더 구성접속·키 관리

한 번의 push, 세 단계의 확인

  1. 01 · 개발 PCmain에 push수정한 내용을 커밋하고 GitHub에 올립니다.
  2. 02 · GITHUB / verify테스트화면·백엔드·배포 스크립트 검사. 실패하면 게시하지 않습니다.
  3. 03 · GITHUB / release빌드·게시이미지 8개를 같은 SHA로 만들어 registry.shnea.kr에 저장합니다.
  4. 04 · NAS / DEPLOY RUNNER운영 배포작업 수신 → 내부 SSH → 이미지 Pull → 갱신·정상 상태 확인.
완료 기준은 deploy 성공입니다. 이미지 게시가 성공했어도 NAS 배포가 실패하면 운영 반영 완료가 아닙니다. GitHub의 verify · release · deploy 세 결과를 함께 확인하세요.

NAS Runner는 배포만 담당합니다. 소스 컴파일·이미지 Build는 GitHub 서버에서 실행하고 별도의 Git/Registry 조회 스케줄러는 두지 않습니다. 개발 PC는 push 후 꺼도 됩니다.

평소에는 이렇게 사용하세요

개발하고 배포하기

  1. 개발 PC에서 ./scripts/dev.ps1로 확인합니다.
  2. 수정 내용을 커밋하고 main에 push합니다.
  3. GitHub Actions에서 해당 커밋의 실행을 엽니다.
  4. deploy까지 성공하면 운영 주소에서 변경 내용을 확인합니다.

이미지 버전 읽는 법

registry.shnea.kr/platform-file-service:<SHA_12>

SHA는 Git 커밋을 식별하는 값입니다. 새 배포는 앞 12자리를 사용하며 같은 태그를 다른 이미지로 덮어쓰지 않습니다.

현재 운영 버전은 아래의 상태 명령으로 확인합니다. 이 설명서에 특정 버전을 고정하지 않습니다.

Pull Request에서는 검사만 실행합니다. docs/STATUS.md만 바뀐 커밋은 배포를 시작하지 않습니다. GitHub의 Run workflow는 main의 전체 흐름을 수동 실행합니다.

NAS 상태와 로그 확인

터미널에서 접속합니다. 주소·포트·계정은 본인의 값으로 바꾸고, NAS 셸에서 NAS_DEPLOY_PATH를 실제 운영 폴더로 지정한 뒤 실행하세요. 실제 경로와 비밀번호는 문서나 Git에 저장하지 않습니다.

1. NAS 접속

ssh <개인_접속_계정>@<NAS_접속_주소> -p <SSH_포트>
cd "$NAS_DEPLOY_PATH"

2. 컨테이너와 현재 버전

sudo sh scripts/deploy.sh status
sudo cat .deploy/current

3. 서비스·배포 로그

sudo sh scripts/deploy.sh logs project-service
sudo tail -20 .deploy/history
sudo tail -20 .deploy/ssh-history

정상 종료 storage-init과 identity-setup은 한 번 실행하는 작업입니다. Exited (0)이 정상입니다.

실패하면 어디부터 볼까요?

실패한 단계운영 상태할 일
verify기존 운영 유지테스트 오류를 고친 뒤 새 커밋을 push합니다.
release기존 운영 유지빌드·Registry 오류를 확인합니다. 일부 게시된 태그를 덮어쓰지 않습니다.
deploy 대기기존 운영 유지GitHub Settings → Actions → Runners에서 Online인지 확인합니다.
내부 SSH 접속·인증기존 운영 유지Runner의 NAS 내부 주소·포트·키·서버 확인 값을 점검합니다.
Pull·이미지 검사컨테이너 갱신 전 중단해당 SHA의 이미지와 Registry 접근을 확인합니다. 설정 파일은 갱신됐을 수 있습니다.
기동·상태 확인일부 갱신됐을 수 있음GitHub deploy 로그와 NAS의 실제 컨테이너 상태를 함께 확인합니다.
release는 성공했고 deploy만 실패했다면

GitHub에서 Re-run failed jobs를 선택합니다. 이미 완성된 같은 이미지를 다시 배포합니다. 전체 워크플로 재실행은 게시된 SHA 덮어쓰기 방지로 거부될 수 있습니다.

이전 버전으로 되돌리려면

먼저 새 push와 진행 중인 자동 배포를 멈추고, 이전 이미지와 DB·설정의 호환성을 확인합니다. 같은 deploy.sh <이전_SHA>를 사용합니다. 전환 전 보호 이미지에 한해 --legacy 0.1.3을 사용할 수 있습니다.

이전 설정은 .deploy/configs/<이전 정상 태그>에 보관됩니다. 필요한 Compose·암호화 환경파일·Loki 설정을 검토해 복원하세요. 이미지를 되돌려도 DB나 사용자 파일은 복원되지 않습니다.

자동 배포를 잠시 멈추려면

GitHub Actions에서 Platform CI and release 워크플로를 비활성화합니다. 재개할 때 다시 활성화합니다. 이미 실행 중인 배포를 중간 취소했다면 일부 컨테이너가 바뀌었을 수 있으므로 NAS 상태를 확인하세요.

운영 폴더에는 실행에 필요한 것만

platform/
├─ 운영안내.html
├─ compose.yml
├─ .env.prod              암호화된 설정
├─ scripts/deploy.sh
├─ infra/loki/loki.yml
├─ .tools/dotenvx
├─ .env.keys     운영 복호화 키
├─ .deploy/              상태·이전 설정
└─ docs/                 상세 설명서

설정과 데이터의 위치

운영 설정
${NAS_DEPLOY_PATH}

DB·파일·로그
${PLATFORM_DATA_ROOT}
하위 postgres / files / loki 폴더에 영속 저장합니다.

이전 자료 보관
${NAS_ARCHIVE_PATH}
이관 백업·이전 구성·일회성 설치 파일. 운영 실행에는 사용하지 않습니다.

별도로 챙기는 환경 파일은 .env.keys 하나입니다. 암호화된 .env.dev·.env.prod는 Git으로 전달됩니다. NAS의 .env.keys에는 운영 키만 둡니다. .secrets 폴더를 따로 옮길 필요가 없습니다.

.deploy는 배포가 자동 기록하며 .deploy/configs는 롤백에 필요합니다. .tools는 최초 도구 설치 위치이고 .playwright-cli는 개발 검증의 임시 출력입니다. platform_tmp에는 이전 평문 환경 백업이 있으므로 접근을 제한합니다.

접속과 키는 이렇게 구분합니다

항목보관 위치용도
Registry 인증정보GitHub Actions Secrets완성된 이미지 게시
배포 전용 SSH 개인키GitHub Actions Secrets정해진 NAS 배포 명령만 실행
NAS 서버 확인 키GitHub Actions Secrets접속한 대상이 실제 NAS인지 확인
운영 복호화 키NAS .env.keysNAS에서 .env.prod 복호화. GitHub에는 전달하지 않음

루트 소유 배포 진입점과 제한된 sudo 규칙은 NAS 관리자가 별도로 관리합니다. 실제 설치 경로·접속 정보는 운영 설정에만 보관합니다. GitHub의 NAS_SSH_HOST는 Runner 내부 접속용이며 개인 PC의 로그인 주소와 다릅니다.

배포 Runner 상태 확인
sudo docker ps --filter name=platform-deploy-runner
sudo docker logs --tail 80 platform-deploy-runner

Runner 등록정보·작업 공간은 전용 Docker 볼륨에 자동 저장됩니다. 별도로 옮기는 키 파일이 아닙니다. Runner에는 Docker 소켓이나 운영 키·데이터를 마운트하지 않습니다. 앱 Compose와 별도이므로 앱 배포 중에도 실행을 유지합니다.
